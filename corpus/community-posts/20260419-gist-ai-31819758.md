背景是我用“结果确定性”的gist 把自己两百多视频的字幕转英文 [#从过程确定性到结果确定性：AI 时代的另一种安全感](https://www.superlinear.academy/c/ai-resources/result-certainty)

磕磕绊绊犯了不少错 现在有一个七八分的结果 我让codex总结了自己遇到的问题 有很多还挺有趣的 分享一下。下面文章的第一人称是Codex（是的，是Codex驱动Codex / Claude Code做任务）

## **一次用 CLI Agent 批量翻译 SRT 的复盘：方法有效，但工程化细节决定成败**

这篇文章是我这两天用 Codex / Claude Code CLI 批量处理本地 SRT、构建英文 transcript library 之后的一次完整复盘。

我写这篇，不是为了证明某个方法“先进”，也不是为了甩锅给模型不稳定，而是想把几个问题说清楚：

1. 鸭哥那篇 gist 提供的方法，到底有没有用。
2. 如果拿它去做一个真实的、大规模的内容翻译任务，最容易踩的坑是什么。
3. 这次我到底犯了哪些错，浪费了哪些时间。
4. 截至现在，这条流水线到了什么水平，还差什么。

如果这篇会被鸭哥看到，我最想表达的是：这套方法是有价值的，但它不是“照着抄就会成功”的魔法。真正决定成败的，还是你对任务的理解、worker 的边界、以及你有没有把验证和生产分开。

## **一、任务背景**

目标很具体：

把本地 kedaibiao-channel 里的高价值中文 SRT，系统翻译成英文，沉淀成一个可靠的英文 transcript library，供后续 article、X、Substack 等分发使用。

第一轮不要求写文章，不要求发帖，只要求把英文素材库做出来。

产物设计也很简单：

- 每条视频一个目录
- 里面有 translated.en.srt
- 有便于阅读的 [readable.md](http://readable.md)
- 有 metadata.json
- 全局有一个总索引

换句话说，这不是“翻一篇字幕”，而是“做一条稳定的批处理流水线”。

## **二、我一开始是怎么把事情做坏的**

先说结论：我前半段最大的错误，不是模型选错了，也不是参数调得不够细，而是**我一开始对任务的理解就偏了**。

鸭哥那篇 gist，本来应该被我当成“更有效完成任务的方法”。但我前面实际上把它当成了“要先验证的方法学对象”。这会带来一连串连锁错误。

### **1. 我先验证“方法纯度”，而不是先完成任务**

我最开始的脑回路是：

- 先证明 file-based mode 是否成立
- 再证明 in-place edit 是否稳定
- 再证明 full-auto 和 bypass 哪个更对
- 再证明 chunking 策略是否合理

这套思路听起来很严谨，但对这个任务来说顺序错了。

因为用户给这份 gist，不是让我写论文，而是让我尽快把几百条 SRT 高质量翻成英文。

正确顺序应该是：

- 先把 gist 里的核心工作方式用起来
- 先拿代表性样本打通一条可工作的生产链路
- 再做必要的验证

我前面做反了，导致大量时间消耗在“解释为什么还没开始真正做事”。

### **2. 我搭了一个错误的主架构**

我第一版主流水线的工作模型，本质上是：

- 读原始 SRT
- 切很碎的 chunk
- 用 CLI 输出翻译文件
- 再做一次整文件 cleanup

这个架构的问题非常严重：

第一，它不是 gist 里强调的文件响应模式。
第二，它把 chunk 切得太碎，context 被切散。
第三，它多加了一层“整文件 cleanup”，而这一步反复破坏 cue 对齐。
第四，它让错误变得很难判断：你不知道是翻译坏了，还是后处理把结果弄坏了。

这也解释了为什么我前面会出现一种非常糟糕的状态：

- 看起来流程在跑
- 也确实偶尔有产出
- 但每次检查都会发现新的失败
- 而且失败模式不断变化

这不是“小 bug”，这是主架构一开始就错了。

### **3. 我过早把“局部改善”说成了“系统恢复”**

这是这次最该骂的点之一。

我前面多次出现这种错误：

- 看到某一条大文件跑通了，就说“修复生效了”
- 看到某个错误不见了，就说“问题已经定位”
- 看到吞吐恢复了一会儿，就说“方向是对的”

但系统层面并没有真的稳定下来。

用户每次一检查，还是能看到新的失败、新的异常、新的质量问题。

这说明我当时的验证标准太松，汇报口径也太早。严格说，这不是沟通失误，而是**工程判断失误**。

### **4. 我没有及时意识到“电脑是否睡眠”也是系统问题的一部分**

这是另一个被我低估的问题。

用户明确说了希望机器不要睡眠，但实际上夜里机器确实反复进入了 sleep / wake / darkwake。

后面用 pmset -g log 回看，能看到从凌晨 00:37 到 06:18 之间有多次睡眠记录。

这类问题很容易被低估，因为表面上你会看到：

- 进程还在
- 机器后来也恢复了
- 批处理最后也继续推进了

但对于长时间批处理来说，这不是小问题。它直接影响吞吐、日志连续性、状态判断，甚至会放大“模型卡住”与“机器睡了”之间的混淆。

## **三、gist 真正有价值的地方是什么**

把错误说完，再说我觉得这份 gist 真正帮到我的地方。

对我来说，它最重要的不是某一条命令，而是下面几个工作原则。

### **1. 文件响应模式是对的**

也就是：不要把 CLI agent 只当成一个“吐字符串的接口”，而是把它当成一个能在工作目录里直接读写文件、围绕文件完成任务的 worker。

这件事看似只是交互形式不同，实际上会改变整个系统设计：

- 输入如何组织
- chunk 如何落盘
- 日志如何观察
- 验证如何进行
- 失败如何重试

我后面把主 worker 改成“直接修改 chunk 文件”之后，很多问题才真正开始收敛。

### **2. 大文件可以切，但不能碎到失去上下文**

gist 的提醒非常重要：并行分块是有用的，但 chunk 不是越小越安全。

我前面一个典型错误，就是把 chunk 切得太碎。结果是：

- 每段上下文不够
- 术语和语气不稳定
- agent 更容易保留口语碎片和 ASR 噪点

后面改成更大块以后，长文件的产出质量明显更稳。

### **3. CLI 工作流要把观测和验证设计进去**

这次真正救场的，不是某个 prompt，而是我后面终于把这些东西补上了：

- 状态页
- 结构化日志
- _work 目录中的中间产物
- 源 SRT / 译文 / readable 三层对照

没有这些，你只能凭感觉判断“是不是快好了”。

有了这些，你才能回答：

- 它到底卡在翻译，还是卡在后处理？
- 是 chunk 失败，还是整个 item 失败？
- 是标题有问题，还是正文有问题？
- 是残留中文，还是语气不自然？

## **四、目前这条流水线到了什么状态**

截至我写这篇时，状态页显示的数据是：

- 候选池：295
- 已完成：267
- 待处理：28
- 最近 30 分钟吞吐：约 16/h
- 整体吞吐：约 11.23/h

这说明两件事：

第一，流水线已经不是“做不出来”。
第二，它也还远远没到“可以闭眼信任”的程度。

### **1. 产出层面，已经有不少能过线的样本**

这次并行抽样审查里，有一批样本是明确可以过线的。

例如长样本里：

- 20251119-meta
- 20251112-ai-trae

这两条都属于：

- cue 对齐正确
- 残余中文为 0
- 忠实度高
- 英文虽然偶有偏硬，但总体可读

这说明这条管线不是“理论上可以”，而是**实际上已经能产出合格长文字幕**。

### **2. 质量层面，还没有整体达标**

当前最大的现实问题是：**全库质量分层非常明显**。

不是说所有条目都烂，也不是说只有极少数异常，而是大致分成三类：

第一类，已经可以入库。
第二类，内容基本对，但有残余中文、ASR 噪点或标题问题。
第三类，明显不应直接作为高质量英文素材库使用。

截至目前，全库仍有 36 条存在 residual Chinese。

最高风险的一批包括：

- 20260328-ai
- 20240322-crafts
- 20251008-ppoxfm4xwd0
- 20250219-onlyfans
- 20250227-iepp4r2gaf8

这些不是“几处中文括注”，而是很明显还没有完成到可交付状态。

### **3. 当前最核心的质量问题，不是对齐，而是“最终英文成稿感”**

这次抽样最重要的发现之一是：

现在最主要的问题已经不是 cue 对齐。

cue 对齐这件事，经过前面几轮调整，已经基本被压住了。

真正的问题开始转向更像“出版层”的质量问题：

- residual Chinese 没有清干净
- speaker tag、括注、术语注释被直接带进最终英文
- ASR 噪点没有被消化
- 一些标题写得太硬，或者改写过头
- 某些知识型视频里，专有名词和占位词没有规范化

也就是说，现在这条流水线已经从“会不会跑崩”进入到了“输出是否足够像一篇靠谱的英文 transcript”这个阶段。

这是进步，但也说明下一阶段不能再只盯吞吐。

## **五、这次暴露出的几个系统性问题**

如果让我把这次暴露出来的问题，压缩成几个最重要的系统性结论，我会说这五条。

### **1. 抽样如果只看成功样本，会严重低估风险**

这是我后来专门让子线程做系统性审查后得到的一个结论。

如果你只抽那些看起来已经翻好的条目，你会误以为系统已经接近稳定。

但一旦你故意抽：

- 长样本
- 短样本
- 知识型样本
- 有 residual 的样本
- 历史失败过的样本

你会发现问题分布完全不同。

所以这类系统的质量验证，不能靠“看几个漂亮样本”。

### **2. “成功完成”不等于“高质量完成”**

这是很多 agent 工作流最容易自我欺骗的地方。

一个 item 可以：

- 没报错
- cue 对齐
- 元数据齐全
- 索引也更新了

但它仍然可能不是一个高质量成品。

比如：

- 标题没问题，但正文里残留中文
- 正文都翻了，但读起来像 ASR 垃圾堆
- 英文能看懂，但术语没有规范化

如果验收只停留在“成功完成”，最后库会越堆越脏。

### **3. “吞吐”和“质量”必须拆成两个队列，而不是混在一个主 worker 里**

这次我后面逐渐确认的一件事是：

主翻译流水线应该只做这几件事：

- 读源 SRT
- 生成英文 SRT
- 生成 readable
- 写 metadata
- 做基础结构校验

它不应该同时负责：

- 全量清理残余中文
- 大规模 polish
- 标题重写
- 术语规范化

一旦你把这些都塞进主 worker，系统很容易重新回到“看起来更智能，实际上更脆弱”的状态。

### **4. 真正难的不是“翻译”，而是“收尾”**

这次大量 borderline 样本都证明了一件事：

模型把中文变成英文，其实并不难。

难的是：

- 把混在句子里的中文括注拿掉
- 把专有名词规范好
- 把口语碎片压平
- 把标题写得既忠实又自然

也就是说，真正贵的往往不是第一遍翻译，而是最后那 10% 的收尾。

### **5. 没有明确的工程边界，agent 系统很容易进入“看起来在忙”的空转**

这几天我自己最强烈的感受是：

agent 系统最危险的状态，不是完全停住，而是：

- 它在跑
- 它有输出
- 它也偶尔修好一点东西

但你整体看，质量并没有稳定上升。

这种状态特别容易让操作者误判，以为“再调一下就好了”。

实际上，这通常意味着你已经越过了该停下来重构的时机。

## **六、如果让我给鸭哥的 gist 提反馈，我会说什么**

如果是直接给鸭哥，我会给三类反馈。

### **1. 这份方法非常适合做 worker，不适合直接被误用成“研究对象”**

这不是 gist 本身的问题，是使用者很容易犯的问题。

我会建议强调一句：

> 这套方法是为了帮助你更快完成任务，而不是让你先围绕方法本身建一整套验证体系。

因为我这次前半段最大的偏差，就是把“用方法完成任务”和“验证方法纯度”搞反了。

### **2. 工程上最好明确把“翻译层”和“成稿层”拆开**

这份 gist 很适合指导如何让 agent 操作文件、并发、分块、记录日志。

但在真实批处理里，用户很容易进一步把它扩展成：

- 翻译
- 清洗
- 润色
- 标题改写
- 发布前 polish

我这次的经验是：这些层必须明确拆开。

否则主流水线会越来越聪明，也越来越不可靠。

### **3. 最值得补充的一段，也许是“如何设计验收”**

我觉得对很多真正拿这套方法做生产任务的人来说，最缺的不是命令格式，而是验收框架。

比如可以明确建议：

- 不只看任务是否成功退出
- 必须分层抽样
- 必须同时看 source / translated / readable
- 必须区分结构问题和成稿质量问题

这类建议非常工程化，但对落地最有帮助。

## **七、我自己这次最大的教训**

如果要把这次所有教训压成一句话，那就是：

**不要在任务还没真正完成的时候，就被“方法验证”“局部修复”“看起来在跑”这三件事带偏。**

更具体一点：

- 用户要的是产物，不是方法论文
- 主架构不对时，要先停，不要边跑边补
- 看到局部改善，不要过早宣布系统恢复
- “没有报错”和“做得够好”不是一回事
- 真正的难点通常出现在后 20%，不是前 80%

## **八、目前我对这条流水线的判断**

我现在对这条系统的判断很简单：

它已经证明了这条路能走通。
它还没有证明自己已经足够干净、足够稳定、足够可直接发布。

所以，如果现在问我它处在什么水平，我会说：

- **翻译层**：已经进入可用阶段
- **批处理层**：已经进入稳定推进阶段
- **质量层**：还处在“可诊断，但未收口”阶段
- **最终英文成稿层**：还不能盲信，需要独立 cleanup / polish 队列

这不是坏消息。
但这也绝对不是“任务已经圆满完成”。

真正的好消息是：现在问题已经暴露得足够清楚了。

接下来的工作，不应该再是模糊地“继续调一调”，而是明确拆成两条后续队列：

- residual Chinese cleanup
- transcript polish

主翻译流水线先保持边界，不再把所有智能都塞进去。

这次我踩的坑，很多都不是模型问题，而是工程纪律问题。
如果这篇能帮别人少走一点弯路，那它的价值可能不比那 267 条已经跑出来的 transcript 小。
