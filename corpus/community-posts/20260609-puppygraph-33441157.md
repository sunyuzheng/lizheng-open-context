Fable 5发布了，重新跑了一下总结，效果很不错：

## 对话 PuppyGraph CEO 刘未末：当 AI 开始查数据，Graph 的时代才真正到来

我和刘未末认识很久了。他刚创业半年的时候，我们其实录过一期视频，但当时没有发——那时他还在早期创业的摸索阶段，我不确定频道前的小伙伴们对这种内容有多大兴趣。两年多过去，他的公司 PuppyGraph 完成了 A 轮融资，客户名单里出现了 Coinbase、AMD、Datadog 这样的名字。这次在我家门口，我们重新聊了一遍：他做的到底是什么，为什么学术界火了十几年的 Graph Database 在工业界一直落不了地，AI 怎么改变了这件事，以及一个纯技术背景的团队是怎么把企业客户一个一个拿下来的。

这场对话的信息密度很高。它同时是三个故事：一个数据库技术的故事，一个 AI 时代基础设施卡位的故事，和一个 IC（个人贡献者）出身的创始人做 to B 生意的故事。下面我尽量按对话的脉络把干货还原出来。

## 一、PuppyGraph 是什么：不搬数据，直接把你的数据库"图化"

未末的自我介绍很简短：PuppyGraph 是一个 graph engine。用他的话说：

> "大家有很多数据在 data lake、data warehouse 或者 database 里。原来如果想做 graph 相关的分析，需要先把它导入到一个 graph database。但我们可以直接连接用户现有的数据库、数据仓库和数据湖，直接进行 graph 数据的分析——直接跑 graph query、graph pattern 和 graph algorithm。"

一句话：你的数据待在原地不动，PuppyGraph 在上面 overlay 一层引擎，把它"图化"。需要复杂关系分析的人在这层之上工作，其他人该怎么用数据库还怎么用。

我第一次听他讲这个方向时，他说过一句让我记到现在的话：**"There's no relationship in relational database."**（关系型数据库里没有关系。）这句话听起来像个段子，但它是理解这家公司的钥匙：所谓"关系型"数据库，其实是以表为存储、以 SQL 为接口的，表里存的是数据点，"关系"是靠 join 临时拼出来的。表达一层关系要一个 join，表达六层关系要六个 join——关系越深，越痛苦。

## 二、Graph 为什么在学术界火、在工业界落不了地

未末 2012 年读数据库方向的博士，他说当时"数据库的会议有一多半都在讨论 graph"。但一个很有意思的事实是：学术界火成这样，工业界却一直没有广泛落地。

他举了一个最直观的例子。如果你想查"课代表和未末认不认识"，用一张关系表加两个 filter 就行了。但如果你想查"朋友的朋友"，甚至六度关系，每深一层就要多 join 一张表。再换一个商业场景：

> "电商有 customer、有 product，还有 order history。order history 物理上是一张表，但逻辑上它其实是 customer 和 product 之间的一种关系，是一条边。比如我想找：哪几个客户同时买了这几个产品，又刷了同一张信用卡——这往往就是一个 fraud。"

我当时补了一句：假设你们公司的反 fraud 系统是 join 六个 table 实现的，那我作为坏人就设置七层关系，你就查不到了。他说对，就是这种感觉。**Graph 的本质区别在于：它描述的是边（关系），而不是数据点。** 关系本身成了一等公民，不需要靠 join 去临时拼。

那为什么这么好的东西落不了地？未末毕业后的第一份工作在 TigerGraph，一家 graph database 公司，干了将近三年。他的观察是：

> "几乎所有的客户都是银行——Bank of America、JPMorgan Chase 这些。甚至前六以外的银行就很少会用了。"

原因有两个。第一，**用户 adoption 非常难**——你不可能让用户为了用你的产品而做数据迁移，对拥有大数据的公司来说这"根本不可能"。第二，**成本太高、速度不够快**。他对比了网络安全场景：安全公司存的数据是机器产生的而不是人产生的，数据量远大于银行的交易数据，这就要求"速度又快的同时成本又很低"，而传统 graph database 两条都不满足。

这一段值得停下来想一想。一项技术在学术界被反复证明"有用"，却在工业界沉寂了十几年——问题不出在技术的价值上，而出在**采用成本**上：数据迁移的成本、运行的成本、人的认知成本。这个判断后面会反复出现，它也是 PuppyGraph 整个产品设计的出发点。

## 三、Google F1：一个外界不知道的"秘密武器"

未末离开 TigerGraph 后去了 Google 的 F1 团队，干了四年。F1 是什么？

> "F1 是一个 SQL core engine，可以查 Google 所有的数据，并且不需要做数据迁移。比如你的 logs 我可以把它当做 table 来查，CSV file 也可以当做 table 来查。"

这个团队的战绩很惊人：

> "我们其实就靠这一招，把内部所有其他的 OLAP 系统全部 deprecate 了。当我们已经支持了七八个数据源的时候，剩下所有有自己数据格式和数据源的组都会来联系我们帮他们集成——因为他们也想跟其他的数据源 join。"

最后坚持到最后的是 YouTube，因为 YouTube 相对独立、话语权大。但未末前两年和前队友吃饭时得知，YouTube 也被迁移过来了——因为 YouTube 想用 AI，它的数据就必须接进来。

我在亚马逊和腾讯都待过，深知大多数公司的数据是不打通的——外面的人以为大公司有数据优势就能干这干那，实际上两边的 table 根本 join 不到一起（Meta 是少数例外，数据相对统一）。**F1 是 Google 一个外界不太知道的秘密武器：用一个统一的查询层，绕过了"统一数据存储"这个几乎不可能完成的任务。** 这也是 PuppyGraph 的思想原型——未末后来的创业想法，本质上就是"把 F1 做成一个 graph 的 interface"。

这段还附赠了两个数据库行业的内幕故事，都很精彩。

**第一个：F1 终结了 NoSQL。** 未末说，当年 NoSQL 火的主要原因是大家觉得 MySQL、PostgreSQL 这类 SQL 数据库在数据大了之后不能无限 scale。然后 F1 发了一篇 paper，讲他们如何在分布式系统上用 SQL 查无限大的数据。"我觉得设计得非常精巧"——SQL 能 scale 了，NoSQL 最大的存在理由就没了。

**第二个：BigQuery 是怎么突然变强的。** Google 内部曾有一个和 F1 竞争的引擎叫 Dremel，它同时也是 BigQuery 的引擎。问题在于，Dremel 服务客户的优先级"肯定是内部客户大于外部客户的"——内部客户方便，工程师升职写 perf 的时候内部客户还能帮忙 peer review、说好话。直到某一刻，Google 领导层意识到 BigQuery 竞争不过 Snowflake，于是做了一个组织决策：把所有内部客户交给 F1，让 Dremel 只支持 BigQuery 这一个产品。

> "之后 BigQuery 的竞争力显著提升。大约在 2020 年左右，你就发现 BigQuery 的市场占有率开始大幅提升。"

这件事我有亲身体感。2023 年我在 Statsig 的时候，我们把整个数据栈从 Azure 和 Databricks 全部迁到了 BigQuery——在我原来的印象里，Databricks 是先进产品，BigQuery 是行将就木，结果发现完全不是：作为一个要 process 大量公司 raw logging 的 A/B 测试平台，我们的吞吐量已经超出了 Databricks 的成本预算，而 BigQuery 在 scalability 和 auto-scale 的平滑程度上设计得非常好，确实省了很多钱。

这两个故事放在一起，揭示了一个不太被讨论的机制：**激励结构决定产品竞争力。** Dremel 的工程师没有做错任何事，他们只是理性地响应了升职机制的激励——服务内部客户回报更高。一个产品的市场表现，有时候不取决于技术，而取决于组织怎么给工程师记功。Google 用一次"分家"解决了这个问题。

顺带一提，未末还讲了个有趣的人才流向：F1 组的人后来很多去了 Databricks，Dremel 组的人很多去了 Snowflake——他猜测原因很朴素，Dremel 组西雅图的人多，F1 组湾区的人多。

## 四、为什么是 2023 年创业：两个 trigger

未末 2022 年开始考虑创业，2023 年正式拉了几个同学从大厂离职。时机的选择来自两个 trigger。

**第一个 trigger：Tabular 被收购，Iceberg 统一了 OLAP 存储。**

Tabular 是 Apache Iceberg 团队从 Netflix 离职创办的公司，做数据湖的存储格式。后来的故事是数据库圈的著名战役：

> "他们可能 revenue 很少很少的时候，被 Databricks 两个 billion 收购了。"

为什么一个几乎没有收入的公司值 20 亿美元？因为 Iceberg 对 Databricks 的业务有巨大威胁。Databricks 相对 Snowflake 最主要的优势是 Lakehouse——计算和存储完全分离，用户更灵活、成本更低。而 Iceberg 开源后，Apple（Snowflake 的大客户）很快加入社区并说服 Snowflake 支持这个格式——Databricks 的护城河眼看要被对手拿走。未末听说的版本是：Snowflake 先开了 offer，Databricks 直接 double。"对双方来讲都是比较凶险的一个操作"——兵家必争之地，必须卡住位。

对未末来说，这件事的意义是技术上的："我原来觉得 graph 去查其他的数据还是比较难的，直到 Iceberg 出现之后，我们觉得这个事儿就比较成熟了——我们当时预测 Iceberg 会某种程度上 unify OLAP 的 storage。"底层存储格式统一了，在上面做一个不搬数据的 graph 引擎才有了地基。

（这里他顺手给观众科普了 OLTP 和 OLAP 的区别：OLTP 是增删改查的事务操作，代表产品是 Oracle、MySQL、PostgreSQL；OLAP 是大规模数据分析，代表产品是 Databricks、Snowflake、ClickHouse、BigQuery。逻辑上都是表，但存储、计算、读写方式、查询优化完全不同，"很多公司试图把这两个 unify 在一起，但大部分都失败了"。我借机坦白了一段往事：刚去 Facebook 时发现旁边的 data engineer 写查询不加 limit，在亚马逊这是不可想象的，我当时单纯以为是 Facebook 算力多到可以挥霍——现在才明白是底层架构针对分析负载设计，不加 limit 也没有很贵。）

**第二个 trigger：ChatGPT 火了，"以后不会有人手写 SQL 了"。**

未末有几个同学做 foundation model（其中一个是千问的 founder）。和他们讨论之后，他做了一个第一性原理的推演：

> "如果是 agent 来分析数据的话，它其实不在乎是 SQL 还是其他的 query language。它需要的是一个全面的 semantic 和 context——有一个 natural language 进来，它自动知道哪些数据需要被 retrieve，然后怎么得到这个结果。"

我把这两个 trigger 和前面的历史合起来解读了一下，他表示认同：**Graph 之前做不起来，一是数据架构本身不支持复杂关系的处理，二是 semantic 的维护太困难，三是会用的人太少。现在 AI 解决了"人不会用"的问题（自然语言变成了接口），Iceberg 解决了"数据要迁移"的问题，剩下"架构支持复杂关系"这一块，正是 PuppyGraph 要补的。** 之前企业不做复杂数据分析，可能不是没有 use case，而是能力和架构都不在位。

## 五、AMD 案例：Agentic Data Analysis 到底怎么做才能上生产环境

公司刚成立时找上门的还是传统 graph 需求，但从去年下半年开始，"大部分找我们的都是做 agentic data analysis 的"。未末说了一句很提气的话：

> "我们拯救了很多 failed 的 tech cycle project。"

他详细讲了实施时间最长的客户 AMD。AMD 在 2024 年初找到他们，那时 Agent 还没火，他们最初想要的是一个 one-shot 的 text-to-SQL。但他们的 director 很有思路，想清楚了最终要的是一个 knowledge graph 之上的 IT Ops Agent：把 ServiceNow、Jira、GitHub、telemetry 的数据接起来，遇到问题直接问——"这个 PR 引发了哪些 issue？最近三个月哪些 ticket 一直没有 solve 并且 block 了其他人？"

PuppyGraph 的做法分两层。第一层是 **ontology**——给所有的 table 做 graph modeling。"ontology 的意思就是 data entity 的 semantic，和 data entity 之间的 relations——这其实已经是一个 graph 了。"第二层是在 engine 上加一个 semantic layer 做审计：

> "这时候就有点像 agent harness 的感觉。当它生成一个错的 query 的时候，我们会在外面进行一个 audit，把错的 query reject 掉，并且把 error message 发回去，进行 self-correction。听上去比较 naive，但是帮助很大——帮很多很大的客户把他们的 agent system 部署到了生产环境里。"

按 graph 来查询有两个好处：生成的 query 会沿着 relations 走，"基本上不会出现 join 错 table 的情况"；错误的 graph pattern 在 semantic 层就会被拦下来。我把它总结成两道关卡：第一道先验证"这句话的逻辑是否 make sense"，第二道才是"对应的 table 是什么、怎么取数"。逻辑先 check 一遍，取数再 check 一遍。

还有一个值得创业者记下来的细节——他们签合同前有一个固定环节：

> "Stakeholder random ask question。如果所有 question 都能回答对，基本上我们就很有希望拿下这个 contract。"

让客户的利益相关者随机提问，用真实问题当验收标准。对一个卖"复杂关系查询"的产品来说，没有比这更诚实的 demo 方式了。

## 六、最核心的技术洞察："Deterministic 的事，不应该让 AI 做"

如果整场对话只能带走一句话，我认为是这一句。我问他：做 IT Agent 的人很多，alternative 的做法效果为什么不如你们？他的回答是：

> "我觉得我们是唯一一个把 semantic layer 和 table 之间的关系这两个事儿 decouple 的。我们的理论是：AI 这时候只需要 ontology。至于这些 data entity 和 relation 到底对应哪些 table、是哪个 column join——这件事不应该由 AI 来解决，因为这事实上已经是 deterministic 的了。"

他用一个小学的例子说明。你想知道"哪个老师教的学生最多"：从 graph pattern 看，就是"从老师出发，有一条边连到学生"，干净利落。但在 table 的世界里，你需要详细描述是哪个 column 和哪个 column join 才表达"教"这个关系；更麻烦的是，现实中还有 normalize 和 denormalize 并存的情况——A 表和 B 表存在，同时还有一张 X 表是 A join B 的结果，查 A、B 还是查 X，产生的 SQL 完全不一样。这些等价关系、这些取数路径，全都是确定性的工程问题，却被现在的主流做法一股脑塞进 prompt 里让 AI 去猜。

> "我们就想，把 deterministic 的部分尽量不让 AI 来做，而是变成一个 engine 来做。"

我的理解是：**Graph engine 描述的是边，SQL 描述的是点；要让 AI 理解点和点的关系，你就需要海量的描述文字，而边本身就是清晰的、去重的。** 在表少的时候这个优势不存在——"如果只有一个表，我们觉得现在 text-to-SQL 已经 work perfectly"——但当客户有上千个 table、关系非常复杂的时候，差距是数量级的。

这个原则的适用范围远超数据分析。当下大量 AI 应用的通病，就是把确定性问题概率化：本来一行代码能精确解决的事，交给模型去"理解"和"猜测"，然后再花十倍的工程量去兜住猜错的后果。**把 deterministic 和 probabilistic 的边界划清楚，让引擎做引擎的事、让模型做模型的事——这是 harness engineering 的核心思想，也是 PuppyGraph 能把客户的 agent 推上生产环境的原因。**

## 七、对 Vector Database 的批评："在猜之上再叠一层猜"

聊到 alternative 做法，未末对当下两条主流路线都给出了一线观察——他的客户"在找我们之前基本上都试过这两个"，所以这些 insight 来自真实的失败案例。

先说 Vector Database 路线。他描述的典型做法是：

> "大家就会把所有的信息、unstructured data、documents 这些原始的数据，不做任何处理，先做一个 embedding 放到 vector database 里。所有的 query 过来，先找一个 similarity——这时候是没有任何上下文的，它只是去匹配。"

问题接踵而至：top k 选小了，召回率太低，拿到的信息不够；把 k 调大，token 消耗量暴涨、context window 膨胀，回答质量反而下降。他半开玩笑地说，这可能是"大模型公司 token 消耗量、revenue 涨得很快的原因"之一。我接了一句：向量化有一万种方法，每种返回不同的结果，top k 又有一万种选法——这是在猜之上再叠一层猜，而且是无脑猜。

更有意思的是他提到的一个反直觉结论：

> "在跟做 foundation model 的同学讨论的过程中——后来我们发现 Anthropic 也一直在提这个事儿——如果直接去 grep MD file，效果反倒要比 vector 的效果好。"

为什么？我们在对话里把逻辑捋了一遍：大语言模型本身就是通过语言理解的，直接拿到原文让它自己理解，是它的 native language；搜索和 indexing 又本来就是成熟技术。在中间插一层向量化，理论上的必要性是存疑的。

那为什么 vector database 还这么流行？未末给了一个坦率的、他自称"个人偏见"的解释：

> "ChatGPT 刚火的那一段时间，所有的投资人都涌向了 vector database——它之前并不怎么受欢迎。这样就有很多 vector database 都融到了钱，他们在市场上的音量就很大，push 这个 narrative。这时候大家可能就会觉得这个就是正确的做法。"

**叙事是被资本音量放大的，而不是被效果验证的。** 他补充了一个佐证：真正活得好的几家 vector database（他点名了 LanceDB、turbopuffer、Zilliz），其实很少做文本，大部分做的是视频、音频这类真正必须向量化的数据，而且都转向了 object storage 架构把成本压得很低；而做文本检索的那批，"成本高、效果又不好"，收钱越来越难。他预计这个状态还会持续一段时间——"毕竟他们抢占了先机，大部分人的第一尝试还是会是这个。"我的总结是：大家太习惯从一个抽象概念出发去理解事情了，而那个抽象概念本身就不太 make sense——故事确实能讲出来，但 doesn't make sense。

## 八、Text-to-SQL 的死穴：1500 个 column 和有限的 attention

另一条路线 text-to-SQL 的问题不一样。商业层面，Databricks、Snowflake 这些大公司都内置了这个功能，而且不需要靠它赚钱——独立的 text-to-SQL 创业公司当年融了不少钱，"现在还 survive 的并不是很多了"。

技术层面的死穴是 context 爆炸。他给了一组具体数字：

> "我们的一个客户在找我们之前，其实只做了 50 个 table 的 context。但这 50 个 table 有 1500 个 column。你需要把每个 column 的详细描述、它的 semantic 是什么、它能不能跟其他 column join、join 的 semantic 是什么，全部写进去。但我们发现大部分 entity 其实对应的是 table 而不是 column——这时候，50 个关键的信息会藏在 1500 个没有那么关键的信息中间。"

后果是什么？

> "这并没有什么理论证明，只是我们从经验上感觉，有的时候 AI 会 lost attention。"

我很认同这个观察：AI 的 attention 是有限的，哪怕 context 再长。东西塞得越多，关键信息的信号就越弱。这其实和上一节是同一个病灶的两种症状——**vector 路线把无上下文的猜测当检索，text-to-SQL 路线把确定性的映射当 context——两者都在让模型承担它不该承担、也承担不好的工作。** PuppyGraph 的解法殊途同归：semantic 进 ontology，映射进 engine，context 里只留 AI 真正需要做判断的部分。

## 九、谁在用：网络安全、ITOps、银行，以及一个关于社交网络的神奇发现

目前最受欢迎的几个场景，未末按热度排了排。

**网络安全**排第一。机器产生的数据量巨大，而问题天然是多跳的关系查询：

> "比如有一个新的 vulnerability 出现了，你就想知道：我有哪些 virtual machine 装了包含这个 vulnerability 的 software，与此同时这些 virtual machine 又 expose to public IP？"

以前这类问题靠工程师维护 dashboard，现在可以直接用自然语言问 agent，甚至接上自动修复的 agent——"把这些 expose to public IP 的 virtual machine 放到防火墙后面"。值得注意的是商业结构：**不是大公司直接用 PuppyGraph 做安全，而是网络安全公司用 PuppyGraph 去服务大公司。**

**ITOps** 是第二类，就是 AMD 那种场景。**银行**是第三类，目前用得多的不是反欺诈（agent 介入实时风控还太慢），而是 underwriting 和 cross-sell：客服接起电话的瞬间，agent 把这个客户的全部相关信息组装好——他有 checking 和 saving account 但没有信用卡，就推荐办卡；他用着无年费卡但消费水平很高，就推荐升级。

然后是我觉得全场最"神奇"的一个发现。我问：social media 和广告不应该是你们最重要的客户吗？直觉上社交网络就是最大的 graph。他说他们也想过这个问题，答案出乎意料：

> "Facebook 有一个产品叫 TAO，相当于是把 graph 翻译成 SQL，跑在 Facebook 的数据库上。它并不能跑 multi-hop 的查询——那为什么 Facebook 觉得它能满足需求？后来我们发现比较神奇的是，social network 反倒很少需要 multi-hop 的 query。比如 LinkedIn，你会看一度好友、二度好友，三度以上其实就是随机选一些返回给你，并不是真的一步一步去 traverse。"

而真正需要追到底的是另外两类场景：

> "银行转账，我想 follow 这笔钱最后去哪儿了，我会直到找到最后一个终点为止。Cybersecurity，我想知道一个 attacker 进来以后一共做了哪些事儿——而不会走了两步之后就停下来。"

这个发现的启发在于：**判断一个市场需不需要你的技术，不能看它表面上像不像你的技术（社交网络"看起来"最像 graph），而要看它的查询深度上有没有不可妥协的需求。** 社交产品对三度以外的关系可以随机糊弄，因为用户不在乎；追钱和追攻击者糊弄一步都不行，因为漏掉就是损失。

我们还聊到一个应景的例子：听说湾区有些 startup 互相刷 ARR，而且不是两两互刷，是五个、十个公司绕成环，常规手段 track 不出来——这正是 multi-hop graph 查询的用武之地。我开玩笑说，照这个思路看，巨头之间互相投资、互相采购，其实也有"自己刷自己"的嫌疑。

这一节里还有一条做 to B 的朋友应该划线的经验：

> "我们去卖给'卖给银行的 vendor'，比直接卖给银行要快很多。"

以及它的姊妹规律：

> "一个 project 的紧急程度，与它是不是 revenue generator 关系很大。如果客户是用我们去 build 他们的产品，他们的 urgency 会很高。"

外部 innovation 比内部快，靠你赚钱的客户比靠你省钱的客户着急。这两条加起来，基本决定了一家 infra 公司应该优先把力气花在谁身上。

## 十、Go-to-Market：outbound 全军覆没之后

聊完技术，我们转向创业本身。先说他们怎么拿客户的——这部分对我频道的很多同学应该最实用。

**第一个客户是 Coinbase，来自一次转介绍。** Coinbase 的一个 SQL vendor 是未末的朋友，听到对方技术团队提了一个需求，说"未末会这个"。当时 PuppyGraph 只有一个 prototype，但"跟市面上其他产品比优势还比较明显，因为我们是唯一能做到的——Coinbase 的图很大，并且他们的东西也很复杂"。先做 design partner，后来变成付费客户。

**然后他们试了 outbound，效果很差。** 失败的方式很值得琢磨：

> "回我们的人其实并不是特别少。但他们会觉得我们的产品很好、技术让他们很惊艳的同时，又觉得一时半会儿用不上。大部分都是这个情况。"

注意，这不是"没人理"，而是"惊艳但不买"——说明问题不在产品，而在时机和需求匹配。和一位曾在 Twitter 做到很高级别的 advisor 讨论之后，他们决定转向 marketing + inbound。结果出乎意料："很多比较大的客户，像我们现在的 AMD、Datadog，都是 inbound 来找我们的。"

Inbound 从哪来？两个渠道。

**Technical blog。** 写法有讲究：

> "我们会写得尽量具体——他们有可能遇到哪些问题，这个问题可以怎么解决。如果我们的解决方法非常 clean，又明显比其他的要好，他们大部分会找我们聊一聊。"

**Event，尤其是借开源社区的力。** 他们在 Iceberg 团队刚离开 Netflix 时就建立了联系，除了工程合作，对方也帮他们做 marketing。后来 Iceberg 社区活动火了，Databricks、Snowflake 这些大公司反而来找 PuppyGraph 合办——大公司内部流程多，看到有人已经把活动办得很好，就直接提供场地，PuppyGraph 负责组织、请嘉宾、买吃的。未末还总结了一条朴实的办活动心法，和我自己办活动的体验完全一致：**场地、嘉宾、吃的——剩下的都是细节。** 通过这个渠道，他们认识了很多"传说中的人物"，比如 Parquet 的 founder——开源项目之间本来就互相依赖（Iceberg 就是用来管理 Parquet file 的），社区是天然的连接器。

Marketing 花钱了吗？"基本上没花吧，买些吃的。"直到去年下半年 revenue 有了确定性，才开始买展位：Databricks 的 Data + AI Summit、AWS re:Invent。Snowflake 的暂时没买——这里有一个微妙的生态观察：

> "Databricks 的 solution architect 对我们更热情，经常给我们带客户。从他们的角度讲，他们还是希望能把大单接下来——我们只是其中的一个 feature，但如果没有我们的话，可能会影响他们整个 project launch。"

我的转述是：**"我解决不了，但我能帮你解决"——那我何不帮你解决了，让你去拿那个大单。** 一个技术上足够独特、足够互补的产品，会让 ClickHouse、AWS、GCP 这样的大平台主动帮你做宣传、写联合 blog、介绍 use case。"你的 technical insight 足够独特、问题解决方式足够 clean 的情况下，你的业务就增长得很舒服。"

## 十一、关于开源的一个反共识判断："开不开源，不是你能决定的"

聊到 Iceberg，我问了一个问题：这种"就缺这么一个东西"的标准件，为什么是 Netflix 做出来的，而不是 Databricks？未末的回答上升到了一个规律层面，我认为是全场最有结构性的洞察之一：

> "很多公司来问我们应不应该 open source。我觉得这个事儿并不是你能决定的。你看比较火的 Kafka、Iceberg、Presto，都是在大公司的时候因为它需要，所以做了这么一个东西。Google 总是最先碰到 big data 的问题，但它很少 open source，它只发 paper——发了 MapReduce 的 paper 之后，雅虎就做了个 Hadoop。Facebook 的 Presto、Netflix 的 Iceberg，都是先遇到了这个问题所以就做了。然后 Apple、Expedia、Pinterest 都来支持这个 project——他们主营业务并不靠这个赚钱，但他们又遇到这个问题。这个时候建一个 open source project 对他们来讲是最划算的：既解决了问题，又不用付给 vendor 钱。"

换句话说，**伟大的开源项目不是"战略选择"的产物，而是结构的产物：最先撞上问题的大公司 + 主营业务不靠它赚钱 + 整个行业都需要一个标准。** 你很难想象 Facebook 或 Netflix 把所有数据放在 Snowflake 里，成本上完全不可接受——所以他们必须自己造，造完之后开源反而是成本最低的选择。这也解释了为什么 Databricks 愿意花 20 亿买 Tabular：标准一旦形成，卡位的价值远超收入。

对创业者的镜像启示是：如果你在纠结"要不要开源"，先问自己有没有处在那个结构里。没有的话，开源既不是护身符，也不是增长策略。

## 十二、销售：创始人自己卖，是"非常不明智"的

PuppyGraph 现在只有一个销售——John Kato，原来在 Neo4j 负责东部所有大客户，行业经验三十年，经朋友介绍加入。一个人怎么够？因为他足够有经验，而且愿意亲自做 presentation 和 demonstration。所有的 lead 都汇到他那里，由他判断哪个有价值、哪个优先级高。

更有信息量的是未末对"创始人自己做销售"阶段的复盘：

> "我们最开始自己做了一段时间，感觉非常的不明智，主要是浪费了很多时间。关键是你很多话不会讲——你可以这样说、可以那样说，那样说就可以多收点钱，但你不会。还有一个问题是，我们不知道哪些是真的能最后变成 contract 的，哪些只是比较感兴趣、随便聊聊。"

企业销售里的坑还包括：客户公司突然 reorg 了；内部最喜欢你们的技术人员离职了；或者一个技术人员很感兴趣，但他没有任何 clout（影响力），根本促成不了 deal。"一个有经验的 sales 因为见过太多了，很快能闻出来。"

值得一提的是他们对待"没有付费能力的用户"的态度：无论会不会变成 contract 都全力支持，想一些 flexible 的方法——reputation 也是重要的资产。

这一段对技术背景创始人的提醒很直接：**销售不是"会聊技术的延伸"，它是一门独立的、靠模式识别吃饭的手艺。** 创始人前期必须亲自下场理解客户，但把"判断 deal 真假、推进流程、定价话术"长期留在自己手里，付出的是机会成本。

## 十三、Marketing：两种 marketing 人，和"聚焦本身就是一种做法"

PuppyGraph 的 Head of Marketing 也是个有故事的人：早年在 Apple 和百度无人驾驶待过，后来在图数据库公司 Dgraph 做 Head of Marketing，一度把下载量做到每个 quarter 一个 million——那时候未末还在竞争对手 TigerGraph，"被他们搞得很难受，但我们关系还很好"。后来他所在的公司被 Databricks 收购，Databricks 没有留 GTM 的人，未末"赶紧把他挖了过来"。

这个人最有价值的地方不是执行某个具体渠道，而是：

> "他知道这个东西怎么做，并且会根据不同产品来想这个东西应该怎么做。比如有的产品更偏向于 top-down 卖，有的更 bottom-up；我的 ICP（理想客户画像）到底是谁；办 event 面向的是谁，写 blog 面向的是谁。"

具体动作其实不复杂：technical blog、event、YouTube 短视频、webinar、定期发 case study 邮件。我替频道里卡在"不知道怎么 reach out 自己的 ICP"这一步的同学追问有没有更多打法——Reddit 自动回复机器人、Product Hunt 打榜、投 influencer 之类。未末的回答反而是收着的：他们 LinkedIn 投放只做过两次（效果其实很好，但预算有限，钱主要花在产品上），其他基本不做。**"聚焦、没有那么多做法，本身也是一种做法。"** 与其铺渠道，不如想清楚谁是真的目标客户。

对照组是他在 TigerGraph 见过的另一种 marketing——从 IBM 招来的人：

> "大公司的 marketing，我觉得它的主要任务是把钱花出去——均匀地、看上去没有什么错误地把钱花出去，而不是想'我一共就只有这些钱，应该怎么用'。"

我对这一派深有同感：这是一个非常 self-congratulatory 的行业——我做了这个、做了那个、花了这些钱、你看这个物料多漂亮——而且很多时候并不懂产品。预算约束反而是小公司 marketing 质量的来源。

（顺便预告：未末说他们这位 Head of Marketing 也给一些创业的朋友做顾问，我们聊好了之后在社区里办一场直播，让他和未末来跟大家聊 GTM，到时候欢迎来提问。）

## 十四、招人：FDE 必须是"产品的一部分，而不是客服的一部分"

PuppyGraph 最近要招的角色，是能跟客户打交道、同时又能写代码的人——FDE（Forward Deployed Engineer）。未末说，他们现在大部分人"同时需要既是 SWE 又是 FDE"。

FDE 这个词最近被用烂了，我正好上周末参加了一场分享，会后和一家公司的 Head of FDE 聊到一个共识，在这里和未末完全对上了：

> FDE 必须自己能上手改代码——改 production 代码。不能是在客户那边搞完以后提一个 ticket，让家里的工程师改。只有自己能改 production 代码的人才叫 FDE。**FDE 是产品的一部分，而不是客服的一部分。** 客服的那一部分，叫 solution engineer。

未末还给了一个旁证：Snowflake 和 Databricks 增长这么快，和他们 solution architect / solution engineer 的工资跟 SWE 差不多高有很大关系——这些人本身能做 SWE 的活，在客户现场不是"指导"，是 hands-on 直接把事干完。很多传统公司自己根本没有程序员，主营业务也不是这个，他们只想看结果——这时候，派去的人能不能直接解决问题，就是成单的关键。

## 十五、卖技术 vs 卖产品：你只看到了卷出来的那一个

对话里有一段小小的交锋，我觉得特别值得展开。未末说了一句："老实说，我觉得卖产品要比卖 technology 容易很多。"我不同意，给了他另一个视角：

**大家看不到卖产品这件事的难度。** 大家能看到的是什么？是卷出来的那一个——"他好成功啊，他做的东西好漂亮啊，他有这么多故事可以讲，这个东西好像我也可以做。"但大家没有看到死掉的那九百九十九个。这是典型的幸存者偏差。

而卖技术的好处是：一旦你的 technical insight 成立，你可以比较舒服地一路骑下去。Databricks 为什么主动给 PuppyGraph 介绍客户？因为这个东西它做不了、也不想做。你在领域里 build reputation，很多东西会自己来找你——因为他们要解决这个问题，而他们需要你的技术。产品不是这样的：今天你做一个，明天别人抄一个。我对未末的局面的判断是一个"顺风局"：technical 人才选得好，随着 AI 的普及和市场对这个能力的需要，作为 vector database 路线的替代品，position 本身会带着公司往前走。

未末对此的回应保持了他一贯的克制——他承认有顺的一面，但也指出了实际的难处，这就引出了下一节。

## 十六、Positioning 的真实困境：当所有人都说自己是"唯一可行方案"

未末描述了一个很真实的处境：

> "基本上找我们的客户，都是已经试过其他方案——比如 Vector RAG 或者 text-to-SQL——fail 了的。这时候其实不是我们在说服他，而是我们在帮他解释这个事儿应该怎么办。"

这听起来是好事（客户带着痛点来），但它的另一面是：PuppyGraph 不在一个 lead position 上，大部分用户很难第一时间想到他们。我说，你们明明应该站出来说"这是唯一可行的方案、我们是最好的方案"——which is true——但用户不会这么想，或者说你们还没有一个这样的 narrative。

他的回答揭示了 to B 市场一个更深的麻烦：

> "上周是 Snowflake Summit，我去看那些 booth——每个人都在说这件事儿，包括 Snowflake 和 Databricks 自己都说'我们是唯一的可行方案'。而且有意思的是，大家说的都是有道理的。可能确实有一些公司在 bluffing，但大部分公司说的都有一定道理——他选择了一个侧面，这个侧面最后能得出来那个结论。"

这正好接上我平时讲课反复说的一点：**说 feature 没有意义，因为只有懂的人才知道你的 feature 是好的。** Snowflake 说一堆 technical 的东西，Databricks 说一堆 technical 的东西，你再说一堆，外行没法判断——除非他是内行。未末自己也很坦诚："我们并不是唯一解决方案。如果只有五个 table，其实所有的方案都 work；但 table 很多、关系很复杂的情况下，我们的优势是非常明显的。"

于是我们当场干了一件事：现场改 landing page 文案。他们最近精简后的版本是 "Enable agents across 3,000 tables"，外加 petabyte、sub-second 这些指标——但这些"更像是 engineer 关心的问题"。我提议改成 "The best solution for over a thousand tables" 这个方向，再把 AI 和 Agent 嵌进去，类似 "The best solution for AI to work across over a thousand tables"，后面再展开解释。他觉得不错。这一小段我保留下来，是因为它示范了一个定位的基本动作：**不要陈述能力（capability），要陈述适用边界（when to choose us）——"超过一千个 table 选我们"比"我们支持三千个 table"好懂十倍，因为前者替客户做了判断。**

另一个相关的话题是竞争：有些老公司发现这个概念好，"从概念上想抄我们，但实际上他们的产品并没有什么变化"，更像是打了一个补丁。未末的态度出乎意料地积极："实际上我们是没有钱来教育市场的，相当于他们在帮我们普及这个概念。"我笑说这很有我做 AI 课程的既视感——很多人会用我们说的话，但后来发现完全不能 deliver 那个东西。**当你确信自己有真东西的时候，模仿者就是你的免费市场部。**

## 十七、融资与心态：IC 创业的难处，和投资人是怎么找上门的

关于融资，未末先讲了一个 IC 创始人都会撞上的墙：

> "感觉跟投资人打交道下来，大部分情况下，在企业里级别很高、管一个很大 org 的人融资要容易得多——第一他们本来就跟投资人认识，第二他们有 business 的经验。如果是纯的技术人员，你很难 convince VC 你是能做 business 的，而且你去拿下客户也会比较难。"

他们最早的投资人是孵化器。但走到后面，规律反过来了——**投资人会来找你**。渠道有三个：一是 VC 都在跑数据监控，网站流量、社交媒体 traffic、Docker 下载量，"他就会说，我们发现你们这个公司最近很有意思，能不能聊一聊"；二是客户介绍——客户公司除了自己的战投部门，VP 和 director 们本来就认识很多投资人，投资人问"你最近看哪些产品比较有意思"，他们就会提到你；三还是朋友网络——他们 A 轮最大的投资机构，两位 partner 分别出自 General Catalyst 和 Redpoint，而具体投他们的那位投资人是 Coinbase 早期员工（一百多号），正是问了还在 Coinbase 的朋友"最近看到什么有意思的产品"，被介绍了过来。客户、口碑、资本，在 to B 世界里是同一张网。

最后聊心态。我问他创业过程中有没有特别艰难的时刻，他的回答是全场最云淡风轻的一段：

> "没有，我觉得整体上来讲还好。我这个人心态比较好，就算有什么不顺的我也比较想得开。特别是我那几个队友说，大不了就倒闭，回家再找工作嘛。"

但他紧接着说了一个微妙的变化：反倒是做着做着，沉没成本高了，进展也好了，"已经做成这样，就很难半途而废了"。最开始支撑他们的是"输得起"，现在推着他们走的是"舍不得输"。这两种状态都健康，而且顺序不能反——**创业初期需要的是低心理负担（大不了重来），中期需要的是不可逆的承诺感（已经走到这里了）。** 他们几个 IC 出身的创始人，靠不拿工资、生活上极度节省撑过了最早的阶段，撑到了客户、收入和 A 轮逐一落地。

## 写在最后

整理完这场对话，我把它的主线收拢成三句话。

第一句是技术的：**让引擎做 deterministic 的事，让 AI 做 probabilistic 的事。** Graph 落地难了十几年，不是因为没用，而是因为采用成本太高；Iceberg 抹掉了数据迁移的成本，AI 抹掉了"人不会用"的成本，剩下的复杂关系处理正好是 graph 的本行。而当下大量 AI 项目的失败，恰恰来自边界划反了——把确定性的映射塞给模型去猜（text-to-SQL 的 1500 个 column），把无上下文的猜测当成检索（vector 的 top k）。

第二句是商业的：**技术足够独特、解法足够 clean 的公司，增长方式是"被找到"。** Outbound 惊艳但不成单，inbound 送来了 AMD 和 Datadog；Databricks 的 SA 主动带客户，因为你帮他拿大单；投资人爬着 Docker 下载量找上门。前提只有一个——你做的事别人确实做不了。

第三句是给人的：未末在 TigerGraph 看着 graph database 卖不动，在 Google F1 看着统一查询层吃掉整个内部生态，然后在 Iceberg 和 ChatGPT 同时出现的那个窗口里，把这两段经历拼成了一家公司。机会不是凭空想出来的，是先在问题里泡了十年，等结构性变化发生时，第一个看懂它意味着什么。

我们和未末约好了，之后会在社区里办一场直播，请他和他们的 Head of Marketing 来聊 GTM 和 ICP 的具体打法。想介绍投资人的、想聊 graph + agent 落地的，也都可以来。

## **03:00｜学术界火了十年，工业界就是不买单**

这期最有意思的起点，是一个巨大的反差。未末 2012 年读博的时候，graph 在学术界已经非常火：

> 基本上当时数据库的会议有一多半都是在讨论 graph。但是这个事儿很有意思的是在学术界虽然火，但是在工业界其实一直没有很广泛的落地。

他博士毕业后，带着「学术界这么火，落地到工业界应该很有潜力」的想法，去了 TigerGraph——一家专门做 Graph Database 的公司。CTO 兼创始人是数据库领域的教授，也是他博士导师的好朋友。听起来方向对、团队对、技术对。

结果干了三年，发现天花板就在那里：

> 用户 Adoption 非常的难，而且大部分时候因为如果只是一个数据库的话，它的成本又非常高。后来我在 TigerGraph 干了将近三年吧，然后几乎所有的客户都是银行，比如说 Bank of America、JPMorgan Chase 这些，甚至可能前六以外的银行就很少会用了。

一个看起来前途无量的技术品类，三年下来只卖给了六家顶级银行。这不是团队的问题，是整个品类碰到了天花板——成本太高、数据迁移太重、用户 adoption 太难。

## **07:00｜在 Google F1，靠一招把所有 OLAP 系统全部 deprecated**

离开 TigerGraph 后，未末去了 Google，加入了 F1 团队——Google 内部的核心 SQL 查询引擎。F1 做的事情，后来成了 PuppyGraph 的设计原型：

> 这个 SQL Core Engine 可以查 Google 所有的数据并且不需要把数据做数据迁移，比如说你的 Logs 我可以把它当做 Table 来查，然后我的 CSV File 可以当做 Table 来查。我们其实就靠这一招把内部的所有的其他的 OLAP 系统全部 deprecated 或者 retire 了。

关键在飞轮效应——当 F1 已经支持了七八个数据源之后，剩下所有有自己数据格式的组，都会主动来找他们集成，因为他们也想跟其他的数据源做 join。连 YouTube 这种在 Google 内部话语权很大、一直独立运营的团队，最后也被 F1 覆盖了。

这段经历给未末的启发很直接：不迁移数据、直接连接现有的数据源，才是正确的架构思路。这也成了 PuppyGraph 的核心设计——不要求用户把数据导入一个新的 graph database，而是直接连接用户已有的数据仓库和数据湖。

## **22:00｜ChatGPT 改变了翻译层：Agent 不在乎 SQL 还是什么**

这是整期最关键的转折点。2022 年底 ChatGPT 火了之后，未末和做大模型的同学们开始讨论一个根本性的问题：

> 我有几个同学是做大模型的，然后有一个我们班还有一个同学是千问的 founder。当时我们就会讨论一些这些问题，他们觉得以后就不会有人在手写 SQL 了。后来我们再想一下如果是这样的话，我们尝试从第一性原理出发——如果 agent 来分析数据的话，他其实不在乎是 SQL 还是其他的 query language，他需要的是有一个全面的 semantic 和 context。

这个判断为什么重要？因为它解释了 graph 技术十几年落不了地的真正原因，也解释了为什么突然可以落地了。

过去 graph 推不动，一个核心原因是「没有人会用」——企业里所有的数据分析师、数据工程师，习惯的都是 SQL。你让他们学一套新的 graph query language，还要把数据迁移到新的数据库里，成本太高。但如果写查询的不再是人，而是 AI Agent，那 Agent 根本不在乎底下跑的是 SQL 还是 graph query。它只在乎：给我完整的语义信息和上下文，让我知道该去哪里找数据、数据之间是什么关系。

Graph 天然擅长描述这种关系。之前 graph 推不动不是因为技术本身有问题，而是使用者这一层没有变。AI 把这一层变了。

## **25:00｜拯救 failed 的 text-to-SQL 项目——AMD 的例子**

理论成立之后，实际效果怎么样？未末讲了 AMD 的案例，他们目前部署时间最长的客户：

> 我们拯救了很多 failed 的 text-to-SQL project。AMD 是去年年初的时候就找我们，那时候 Agent 还没有火。他们想要的是一个 one-shot 的 text-to-SQL。后来他们的 director 其实很有思路，他们想的是——我其实需要的是一个 knowledge graph。因为他们最终想做的是一个 IT Ops Agent：我有 ServiceNow 的数据、Jira 的数据、GitHub 的数据、telemetry 数据，然后有一个 IT Ops Agent，当我遇到问题就可以问它——比如这个 Pull Request 引发了哪些 Issue，最近三个月哪些 Tickets 一直没有解决并且 Blocked 了其他人。

AMD 的这位 director 想通了一件事：要让一个 Agent 回答「这个 PR 引发了哪些 Issue」这种跨系统的关联问题，光靠 text-to-SQL 是不够的。你需要先把 ServiceNow、Jira、GitHub 这些系统之间的关系建模出来——谁提交了什么、什么关联了什么、什么阻塞了什么。这就是 knowledge graph。

而 PuppyGraph 的价值是：你不需要把数据搬到一个新系统里，直接在现有数据源上建一层 graph，Agent 就能沿着这些关系去查询。

## **31:00｜为什么 Vector DB 在这类问题上不行**

这一段我觉得特别值得单独拎出来看。因为现在很多人一听到 RAG，第一反应就是：把数据丢进 Vector DB，做 embedding，top k 召回，然后交给大模型。未末的判断很直接：这个做法在很多企业数据分析场景里并不成立。

他说现在很多客户在找 PuppyGraph 之前，基本都试过两类方案：一种是 Vector Database / Vector RAG，另一种是 Text-to-SQL。Vector DB 的典型做法，是把 unstructured data、documents 这些原始数据不做太多结构化处理，先 embedding，放进 Vector DB。问题是，query 进来之后，它先做的是 similarity 匹配：

> 这时候是没有任何上下文的，它只是去匹配。如果 top k 发给 large model 的 top k 小了，就会出现召回率太低，因为它是在猜之上再叠了一层猜，而且是一个无脑猜。

这句话很关键。Vector DB 的问题不是「完全没用」，而是它的错误来源和企业关系型问题的要求不匹配。你要问一个 IT Ops Agent：「这个 Pull Request 引发了哪些 Issue？最近三个月哪些 Ticket 一直没有解决，并且 block 了其他人？」这不是一个“语义相似”的问题，而是一个跨系统、跨实体、跨关系的精确追踪问题。它需要知道 PR、Issue、Ticket、ServiceNow、Jira、GitHub、telemetry 之间的确定关系，而不是找几段看起来相似的文本。

未末进一步说，Vector DB 的调参会把问题推到另一个方向：如果 top k 太小，召回不够；如果 top k 变大，token 消耗量和 context window 都变大，质量还会掉下去。于是系统看起来更“全”，但实际上把更多不确定材料塞给模型，让模型在噪音里继续猜。

> 如果 top k 的 k 选小了，他们就会因为拿的信息不够把 k 变大。但 k 变大对应的就是 token 消耗量也会特别多，context window 特别大，然后质量掉下去。

所以这段的重要性在于，它把「为什么 graph」讲得更清楚了。PuppyGraph 不是在说 Vector DB 这个品类不行，而是在说：当问题本质是复杂实体关系、确定路径、跨系统追踪时，用 similarity 去近似关系，会天然吃亏。你需要的是把语义层和数据关系建模出来，再让 Agent 在这个结构上工作。

## **39:00｜核心洞见：把 deterministic 的部分不让 AI 做**

整期视频技术含量最高的一段，是未末解释 PuppyGraph 和其他方案（Vector RAG、Text-to-SQL）的本质区别。

在讨论中，我试着用自己的理解做了一个类比——Graph 的引擎描述的是「边」（关系），SQL 描述的是「点」（数据表）。你要用 SQL 描述点和点之间的关系，需要写大量的 join 和上下文描述；但如果你用 graph 来描述，关系本身就是清晰的、去重的。未末确认了这个理解，然后讲了一个更精确的能力边界：

> 在没有复杂关系的时候是没有什么优势的。比如说我只有一个表，我们觉得现在 Text-to-SQL 已经 work perfectly。但是比如说我们很多客户有上千个 table，然后关系也非常复杂，这个时候做 context 其实是非常难的。我们就想——把 deterministic 的部分尽量不让 AI 来做，而是变成一个 engine 来做。

这句话是整期最核心的设计哲学。

Text-to-SQL 的做法是：把所有表的信息（每个表有哪些列、列的语义是什么、哪些列可以和哪些列 join）全部塞进 AI 的上下文窗口，让 AI 自己判断。五个表的时候这没问题。但当客户有上千个表、每个表几十列、总共几万个 column 的时候，AI 的注意力会被稀释——关键信息淹没在海量的不那么关键的信息里。

PuppyGraph 的做法是把这件事拆成两步：AI 只需要理解语义层——老师和学生是什么关系、订单和客户是什么关系；至于「这个语义关系对应的是哪个 table 的哪个 column，join 条件是什么」，这些确定性的事情交给 engine 来做。AI 做 AI 擅长的理解和推理，engine 做 engine 擅长的精确匹配和计算。

## **44:00｜社交网络反倒很少需要复杂的 graph 查询**

这是一个漂亮的反常识判断。大多数人一听 graph，第一反应是社交网络——Facebook、LinkedIn 不就是最典型的 graph 应用吗？未末在实际做产品的过程中发现完全不是这样：

> 后来我们发现比较神奇的是 Social network 反倒很少需要 multi-hop 的 query。就比如说 LinkedIn 你会选一度好友、两度好友，不会三度好友了，之后就是三 plus。其实后边就是三 plus——就是随机选了一些，没有意义了。

社交网络的关系查询其实只需要走两三步就停了。LinkedIn 给你推荐的三度以外的好友，本质上是随机选的，并不是真的沿着关系图一步步找过去的。Facebook 内部的 Tau 系统也是类似的思路——把 graph 翻译成 SQL 跑就够了，不需要真正的多跳查询。

但银行和网络安全完全不同：

> 银行比如转账，我想 follow 它的钱最后去哪儿了，我会直到找到最后一个终点为止。然后包括 cybersecurity，我就想知道一个 attacker 进来了以后最后一共做了哪些事儿，而不会再走了两步之后就停下来。

反欺诈追踪转账路径、网络安全追踪攻击者行为，这些场景需要沿着关系链一直追到底。这才是 graph 真正有压倒性优势的地方。

## **46:00｜创业冷启动：从 Coinbase 到 Databricks 主动推荐客户**

未末的创业故事有一条很实际的线索：纯技术背景的 IC 出来创业，怎么拿到第一批客户？

> 我们几个都是 IC，跟投资人打交道下来我觉得大部分情况下还是在企业里做的级别很高、比如说管一个很大的 org 的时候融资要容易得多。如果是纯的技术人员，你很难 convince VC 你是能做 business 的。

他们的第一个客户 Coinbase，来自朋友推荐——Coinbase 的一个供应商在跟技术团队讨论时提到有这么个需求，而那个供应商恰好认识未末。后来也做过 outbound，但效果很差。转折点是他们开始写技术 blog、办 Iceberg 社区活动，让大客户通过 inbound 找上门来。

有意思的是 Databricks、AWS、GCP 这些大公司反而会主动帮他们推广、一起写 blog、一起办活动。原因很实际——这些大公司自己做不了或不想做 graph 这层，但客户有这个需求。PuppyGraph 帮他们补上了这块能力，他们拿到更大的单子，是双赢。

> 从他们的角度讲他们还是希望能把大单接下来。我们只是其中的一个 feature——如果没有我们的话，可能会影响他们整个 project launch。

## **01:01｜市场的真实困境：Feature 没有意义**

最后一段特别值得技术创业者听。PuppyGraph 在技术上确实更好，但市场认知还没跟上：

> 基本上找我们的客户都是已经试过其他一些方案比如说 Vector RAG 或者是 Text-to-SQL fail 了。这时候相当于不是我们在去说服他，而是我们在帮他解释这个事儿应该怎么办。但是其实对大部分用户来说他们很难第一时间想到。

更扎心的是，当所有人都在喊「我们是唯一正确方案」的时候，feature 对比反而失去了意义：

> 用 AI 讲课的时候就是我说 feature 没有意义。因为 feature 是懂的人才知道你的 feature 是好的。一个不懂的人没有办法比较这个 feature 和那个 feature 之间哪个好。

Snowflake Summit 上每个 booth 都在说自己是最佳方案，包括 Snowflake 和 Databricks 自己也在互相攻击。在这种环境里，一个技术创业公司再怎么列 feature 也没用——用户只有亲手试过别的方案、失败了，才会认真听你的解释。

这不只是 PuppyGraph 的困境。任何有真正技术壁垒的创业公司，都会遇到同样的问题：你的东西确实更好，但市场得自己走完那段弯路才会回来找你。

## **01:06｜融资不是只靠 pitch，客户和 traction 会把投资人带来**

后面聊到融资，未末讲了一个很 B2B 的现实：当你真的有客户、有使用、有行业里的口碑，投资人并不只来自创始人主动 pitch。

> 你的客户基本上也会给你介绍投资人。除了他们自己公司的 strategic investment 部门，他们自己的 VP 或者 director 也会认识很多投资人。投资人问他们最近看哪些产品比较有意思，他们也会给你介绍。

这背后有一个更实际的机制。投资人也会看各种外部信号：网站流量、social network traffic、Docker downloads。对 to B 公司来说，这些不一定直接等于收入，但它们说明一个东西正在被行业注意到。

未末讲 A 轮投资人的来源时，也不是一个标准的「路演故事」，而是通过客户和行业网络转出来的：投资人去问 Coinbase 的朋友最近看到什么有意思的产品，朋友正好介绍了 PuppyGraph。这种融资路径很适合技术基础设施公司——你不一定一开始就有漂亮的消费级增长曲线，但如果真正懂这个问题的人开始互相介绍你，融资网络会自己打开。

## **01:09｜他们要招的人：既是 SWE，也是 FDE**

尾声里聊到招人，未末说他们需要的是能同时跟客户打交道、又能写代码的人。他用了现在很流行的词：FDE。但我和他都觉得，这个词已经被用烂了，所以要重新定义一下。

> FDE 必须自己能上手改代码。他不能在客户那边完了以后提一个 ticket，然后让家里的工程师改代码。只有自己能上手改 production 代码的人，才叫 FDE。他一定是产品的一部分，而不是客服的一部分。

这句话很重要。很多公司把 FDE 理解成高级售前、解决方案工程师、客户成功的混合体。但对 PuppyGraph 这种产品来说，客户的问题往往不是「教他怎么点按钮」，而是要在真实系统、真实数据、真实业务约束里把东西跑通。这个人如果不能改 production 代码，就只能把问题传回公司内部，反馈链条会变长，判断也会失真。

所以未末说他们现在很多人需要同时是 SWE 和 FDE。这其实也是 AI 时代 enterprise infra 的一个变化：产品还在快速演化，客户现场就是产品定义的一部分。能把客户需求翻译成产品改动、并且自己把改动做出来的人，会比传统的支持角色更关键。

## **01:12｜早期 marketing 的价值，不是把钱花出去**

最后一段聊 marketing，我觉得对技术创业者特别有用。未末讲他们的海外 marketing 负责人之前在 Dgraph 做过 Head of Marketing，后来上一个公司被 Databricks 收购，正好加入 PuppyGraph。这个人最有价值的地方，不是会做某一个动作，而是知道不同产品应该怎么做 marketing。

> 他知道这个东西怎么做，并且会根据不同产品来想这个东西应该怎么做。我的面向人群到底是谁？谁是我的 ICP？办 event 面向的是谁，写 blog 面向的是谁，这都有很大关系。

这和大公司 marketing 很不一样。大公司有预算、有流程、有品牌资产，marketing 很容易变成「把钱花出去」：办活动、做物料、投广告、做一个看起来没有错的 campaign。但创业公司没有这个奢侈。预算有限反而逼着团队取舍：哪些活动真的触达目标客户，哪些 blog 能被正在找答案的人搜到，哪些 event 能让 ecosystem 里的关键人开始认识你。

所以这期结尾其实回到了同一个主题：PuppyGraph 的增长不是靠把所有渠道都试一遍，而是反复判断「谁是真的目标客户」。技术创业最容易犯的错，是以为只要技术足够好，懂的人自然会来；但这期访谈反复提醒的是，技术 insight、产品表达、客户教育、生态合作、FDE 和 marketing，其实是一条连续的链。

## **这期最值得带走的判断**

这期聊了很多技术细节，但最有价值的是一个关于 AI 基础设施的结构性判断：AI Agent 改变的不只是应用层，它也在重新定义底下每一层基础设施的价值。Graph 技术十几年来一直在等的，不是更好的算法或更快的引擎——而是「谁来写查询」这件事发生根本性的变化。当写查询的从人变成了 Agent，很多过去推不动的技术方向，突然就通了。

而未末在这个判断之上，还叠了一层更精确的设计哲学：AI 做理解和推理，engine 做确定性的匹配和计算。不是让 AI 做所有事，而是让每一层做自己最擅长的事。

这期另一个值得带走的点，是技术创业的落地过程本身。PuppyGraph 的故事不是「有个好技术，然后市场自然买单」。它更像是一个完整链条：在 Google F1 里验证过架构直觉；在 AI Agent 出现后重新找到使用者；用 AMD 这样的客户案例证明价值；通过 Iceberg 生态、technical blog、event 和 partner 获客；再用 FDE 和 startup marketing 把客户问题真正吃下来。这个链条，对所有在 AI 时代做基础设施的人都有参考价值。
