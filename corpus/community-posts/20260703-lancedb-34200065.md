这期我请到的嘉宾是佘昶，LanceDB 的 CEO and Co-Founder，也是 pandas 项目的第二作者（数据同学们可以在这里向他表示感谢）。

他长期做 ML/AI data tooling；从 pandas、Hadoop，到 TubiTV 的 machine learning 和 experimentation platform，再到现在的 LanceDB，他一直在处理同一个问题：数据系统怎么让研究和实验跑得更快。

所以这期表面上聊 LanceDB、Lance Format、Parquet、向量数据库、多模态，真正串起来的问题是：当模型继续变强，AI 的瓶颈会不会越来越落到数据质量、数据混合、数据检索、实验管理和 research velocity 上？

这对很多观众都很重要。做 AI 产品的人会关心，为什么图片和视频模型看起来很强，落地时却还不够可控。做 infra 的人会关心，为什么 Parquet 这样的成熟格式，在 AI training data 场景里会不够用。做开源公司的人会关心，开源到底什么时候是优势，什么时候是负担。做研究和创业的人会关心，前沿 AI team 买 infra，买的到底是软件，还是时间。

## **00:50｜AI 进步开始转向数据和研究循环**

一开始 佘昶 介绍 LanceDB 时，没有把它讲成一个普通数据库。他说 LanceDB 要帮 research labs 改善 multimodal data experience，尤其是 pretraining 的 data flywheel。

他的判断很直接：

> “pretraining 的很多 model improvement，都会从数据的 improvement、data quality、data mixtures 这些方面来。”

所以他们要把 research 层面的问题和 inference 层面的问题拆开，让 research teams 能更有效地用 research agents 做 recursive research loop。

这段值得从开头看，因为它给后面所有技术细节定了位置。这里谈的不是“数据重要”这种泛泛判断，而是 AI research 的生产方式正在变：模型提升越来越依赖数据怎么被生成、筛选、搜索、回填、重新实验。谁能让这个循环更快，谁就能更快推进模型。

## **02:30｜训练数据不是一个文件夹，是一套系统**

我问他，既然很多数据公司都想帮 research lab 做 infra，LanceDB 跟 Databricks、BigQuery、AWS 或者 lab 自己做的东西有什么不同。

佘昶先从 pretraining 数据本身讲起。训练数据不只是 raw data。里面有 web crawl、视频、音频这样的 asset data；有 timestamp、events 等 metadata；有 feature engineering 做出来的 feature enrichment；还有支持 data curation 的搜索数据，比如 scene description 和 embeddings。

他说：

> “很多 research time 都花在比较底层的 data infrastructure、data pipeline 上面，而不是真正去做 high-level research experimentation。”

这句话很关键。外部看 AI research，容易只看到模型、论文和 benchmark。但实际工作里，研究人员大量时间会被数据搬运、格式转换、系统连接、pipeline 执行吃掉。训练数据不是把文件扔进一个目录，它是一套持续变化的系统。

如果这套系统慢，research loop 就慢。

## **08:00｜自动驾驶长尾问题：模型犯错以后，怎么把同类数据找回来**

这一段是全期最容易理解 multimodal retrieval 的地方。

佘昶用自动驾驶举例：下雨天，旧金山白天，一个十字路口，路边有个小孩穿绿色雨衣，模型却把他识别成树冠。接下来团队要做的事情，不只是修一个 label，而是把类似场景找回来，做 data mining 和 data creation。

他的原话是：

> “你怎么去搜索这些、找到这些数据，就是一个比较复杂的 retrieval 问题。”

这就把“多模态搜索”从抽象数据库概念，变成了模型犯错后的真实工作流。模型在长尾场景里犯错，团队要找更多相似数据：同样的天气、城市、时间、路口、物体、误判类型。这里需要文本、图片、视频、metadata、embedding 一起工作。

这也是 LanceDB 这类系统想解决的问题：AI training data 的搜索，已经不是传统数据库里查一行记录那么简单。

## **09:00｜Parquet 很好，但它服务的是另一类工作负载**

我在这里从一个普通数据科学家的视角问他：很多人理解数据，最开始就是理解文件后缀。CSV、Excel、Python data file，后来接触 AWS，才知道 Parquet 这种格式。那 Parquet 到底是什么？为什么 AI 场景里会不够用？

佘昶解释，Parquet 是十多年前由 Cloudera、Twitter 等公司推动出来的列式存储格式，现在是 analytics、BI data 的 industry standard。它做 sequential scan 很快，很适合 OLAP 和 BI。

问题出在新的 AI workload 上。

AI 数据经常需要快速点查、搜索、抽取少量长尾样本。比如从十个 billion rows 里找十个能解决长尾问题的样本。Parquet 面向 sequential scan，做这种 random access 会很慢。

另外，AI 数据里常常小列和大列混在一起。小列可能是 spam score、perplexity score；大列可能是图片、视频。Parquet 的 row group 设计要求不同 columns 在同一个 row group 里，调小了不适合大内容，调大了又拖慢扫描。

所以佘昶的态度并不是说 Parquet 失败了。他明确说，如果你的 use case 还是 BI 和 OLAP，没有必要换，Parquet 做得很好。Lance 要服务的是需要 search、multimodal storage、training data management 的场景。

## **12:00｜Lance Format 改了什么：点查、大小列混合和 row group**

接下来佘昶讲 Lance Format 和 Parquet 的关键差别。

第一，data layout 不一样。Parquet 的 data 和 offset 是 interleaved 的，做点查时至少要读出一个 row group。Lance Format 把 data 和 offsets 分开，先读 offsets，就能知道 exact byte range，然后直接读某一行、某一列的数据。

他说这基本上是：

> “constant-time random access lookup。”

这对 training 里的 shuffling、search、data curation 都很重要。

第二，他们后来去掉了 row group 限制。早期 Lance Format 也有 row group，后来用 Rust 重写之后，第二个版本把 row group 取掉了。不同 columns 可以有不同的 chunks 和 rows，再用 file metadata 和 statistics 来解决 row alignment。

我问他，Parquet 有没有可能做到这一点。

佘昶的回答很像一个做数据格式的人才会说出来的话：

> “他做到这点他就不是 Parquet 了。”

原因也很现实。Parquet 是一个历史很久的 project，核心 architecture change 很难；不同语言里已经有不同实现，出现了比较严重的 fragmentation。如果再做底层核心变化，会给整个 community 带来很大困惑。

这段不是在攻击成熟标准，而是在解释成熟标准的边界。一个格式越被广泛使用，越难做破坏性改动。新 workload 出现时，新格式有时不是因为旧格式不好，而是旧格式已经很难变成另一种东西。

## **20:00｜Delta、Iceberg、Lakebase 和 Lance 各在什么位置**

我接着问 Delta Lake、Iceberg、Lakebase 这些名字到底怎么理解。

佘昶先把 file format 和 table format 分开。Parquet 是 file format。Delta 和 Iceberg 是 table format，它们用 metadata 把多个 Parquet files 组织成一个 table，让用户在更高层看数据。

但它们主要服务 traditional data engineering 和 BI 场景。到了 ML experimentation 和 model training，就会遇到新的问题。

比如 feature engineering。研究人员会不断加 columns，做 backfill，跑不同版本的 feature。如果用 Delta 或 Iceberg，添加 column 可以，但 backfill 往往要重写 table。Lance 的 table format 支持 two-dimensional data evolution，可以增量做 backfill，原有数据列不用重写。

还有 table branching。佘昶说，越来越多 researcher 想通过 agents 做 massively parallel data experimentation。比如一个 spam score 有一百种算法，每种算法有不同参数，要并行跑 variants，再进入 evaluation loop。多个 researcher、多个 idea、多个 branch 同时存在，metadata isolation 和 contention 就变得很重要。

这段把 Lance 的位置从“检索快”扩展到了“实验管理”。AI research 不是训一次模型，而是在大量数据版本、feature 版本和实验分支里反复试错。

## **26:00｜LanceDB 不是只做 vector database**

我问佘昶，很多人会把 LanceDB 归类成 vector database，他怎么看。

他说 search 确实是 LanceDB 很重要的 use case，但 LanceDB 作为数据平台，远远超过 vector database。

原因很简单：如果单独用一个 vector database，你要把 embeddings load 到另一个系统里，搜出来的结果还要再接回原来的数据和流程。对 research organization 来说，这会增加复杂度。

佘昶说 LanceDB 想做的是一套数据平台：支持 search，也支持 geospatial search、time series filtering、data production pipeline，以及 distributed execution。

他举了一个很实际的例子：researcher 让 agent 给一个大 table 去重，agent 可以写出很好的 Spark job，但它不知道怎么 tune Spark cluster。数据多大、job 长什么样、要多少 node、多少 CPU、多少 RAM，这些都会拖慢 research velocity。

所以 LanceDB 想把 distributed execution 接过去，让 agent 只写一个小的 Python UDF，剩下的 resilient distributed execution 由平台完成。

这段能纠正一个常见误解：LanceDB 不只是 RAG 里那一步向量检索。它想做 AI research data platform。

## **30:00｜技术选择一定有 tradeoff**

我问他，Lance 比 Parquet 的 tradeoff 是什么。总不能全是好处。

佘昶说，早期 Lance Format 没有优先做 compression。如果只存 tabular data，Lance 的数据可能比 Parquet 大，两三倍都有可能。

但他们当时优先服务 multimodal data。一个表里如果有图片、视频这样的 column，整个 dataset size 会被这些内容主导，而图片视频本身通常已经有 JPEG compression 或视频压缩，外面再加一层 compression 意义不大。

后来随着更多客户加入 LLM training text data，他们加了 block-level encoding 和 compression。在不降低点查速度的情况下，文本数据压缩后有些场景已经可以比 Parquet 小。

这段很重要，因为它避免把新技术写成“全都更好”。好的 infra 判断通常来自清楚的场景选择：早期优先 multimodal 和 random access，后来再补 text compression。每个阶段先服务最痛的 workload。

## **33:45｜开源公司要连续打两个 homerun**

中段我们聊到商业模式。LanceDB 是开源公司，但佘昶对开源没有浪漫化。

他引用 Databricks CEO Ali Ghodsi 的观点，说自己非常同意：

> “如果一个 founder 能不开 open source company，就不要 open source。”

他的比喻是，做开源公司像打棒球，一上来就要 hit homerun。而且开源公司要连续打两个 homerun：第一个是 open source adoption，第二个才是 monetization。

更麻烦的是，这两个 homerun 需要的能力完全不同。开源 adoption 要 community、developer experience、distribution；商业化要产品、销售、企业需求、付费价值。

所以他的建议很克制：

> “Only do open source if it’s the only way to win.”

那为什么 LanceDB 仍然开源？佘昶给了两个理由：distribution 和 standardization。如果你的开源项目有机会成为 new standard，或者成为非常有效的 distribution channel，开源才可能成立。再加上他和 co-founder 都有长期开源经验，知道一些坑，也愿意承担这条路的复杂度。

这段对创业者很有价值，因为它拆掉了“开源天然更好”的想象。开源是一个赢法，但只有在它确实能带来标准化和分发优势时，才值得承受额外难度。

## **36:00｜开源商业化 3.0：开源项目和付费产品要分开**

佘昶接着把开源商业化分成几代。

1.0 是卖 support。你有一个开源软件包，商业化靠 support、private development。

2.0 是 Elastic、Redis 这类，在服务周边卖 acceleration、security、compliance、scale-up、enterprise features。问题是大厂可以拿你的开源项目，直接做成自己的托管服务。你能做 security，大厂也能做。

3.0 的特点是，open source project 和 monetization 的东西分开。比如 LanceDB 的开源部分在 storage 层，商业化在 compute 和 data management 层。

他给了一个很清楚的判断标准：如果大厂拿走你的开源部分，用现有资源三个月内就能复制你的服务，那这个商业化层太薄。佘昶认为 multimodal lakehouse 不可能这么简单复制。

这段把技术护城河和商业模式连到一起。LanceDB 不只是“开源一个项目，再卖企业版”。它要让开源层成为标准和入口，把付费价值放在更难复制的数据管理、计算和平台能力上。

## **40:00｜Adoption 的难点：从 early adopter 走进主流数据栈**

我问他，既然 LanceDB 开源做得不错，也有 MidJourney、Runway 这样的客户，为什么不是所有 AI 公司都已经在用。

佘昶说，ByteDance 等大公司也已经在用或开始用。现在的问题更多是时间和 maturity。

在 early adopter 群体里，LanceDB 已经有很高知名度。大家知道它在 multimodal data training、AI search 这些场景里的价值。下一步是 mainstream adoption。

这件事不只靠技术本身，还要做 customer education、community education，以及更深的生态集成：Spark、Ray、predicate pushdown、catalog、Unity Catalog、Polaris、Gravitino 等。

他说，如果传统 engine 用不到 Lance 的 format indexing、快速点查这些特性，那跟 Parquet 的差别就体现不出来。所以 integration 要做深，要让企业已有的数据管理、权限、catalog、计算系统都能接进来。

这段说明了基础设施扩散的真实难度。一个新格式技术上成立，只是第一步。它还要进入企业已有的数据栈，跟已有组织方式和平共处。

## **44:15｜Research lab 最贵的不是云成本，是时间**

我问他，像 OpenAI 这样的公司如果觉得 format 重要，会不会只用开源 Lance Format，然后自己搭一套？

佘昶说不一定。因为对 research 来说，最重要的是时间，不是 monetary cost。

他的例子很具体：

> “你有一个十个 billion row 的 table，那你怎么去做分布式的索引创建，然后分布式的 search？这种大量的、大吞吐量的 search，难道你会想去花精力、花时间，再雇一个专门做 database 的团队来把这个东西搭上去？”

这句话把 LanceDB 的商业逻辑说透了。前沿 lab 付费买的不是一个小工具，而是让研究团队不用把注意力花在底层 database engineering 上。

如果一个 infra 能把 research velocity 提高两三倍，它对应的价值不能只按云成本算。研究人员、工程团队、实验周期，这些时间成本更贵。

## **45:35｜多模态还不够 native，图片生成还没有 ChatGPT moment**

技术和商业聊完后，我问佘昶怎么看多模态。

他的判断是，现在很多多模态并不 native。很多时候，大家只是把文件变成 text，再在 text 上做各种事情。

他接着讲图片生成：

> “它可能缺少一个我们把它叫做 ChatGPT 的 moment。”

文本模型的厉害在于，你可以让它“指哪打哪”，很有效地 steer conversation。图片生成这几年进步很大，但还没有完全到这个状态。

他说 MidJourney 生成的图片非常漂亮，但问题是：

> “Is it going to do what you told it to do?”

也就是说，漂亮和可控是两件事。如果不能指哪打哪，设计、营销这些大众 use case 就只能落地一部分。

这段能把底层数据问题接到普通用户的体感上。我们都能感觉到图片模型很惊艳，但它还没有像 ChatGPT 改变写作和编程那样，稳定改变设计工作流。原因之一就是 steerability 还不够。

佘昶也补了一句边界：传统 image generation 的方向，很多团队会把它看成 engineering 问题，需要更多 training data、更好的 data curation、更好的 post-training。至于模型架构会怎么变，他没有假装给出确定答案。

## **49:40｜视频和 world model：模型还没有理解物理世界**

视频和 world model 这一段更往前沿走。

佘昶说，视频可能是另一个问题。视频生成里，模型不知道 physical world，所以会出现穿帮：一个杯子这一帧在这里，下一帧可能飞到房间另一边。

他的说法是：

> “这个模型没有一个 physical understanding of the world，没有一个 physics engine。”

所以 world model 会变得重要。它可能支持机器人，也支持那些必须理解物理世界的场景。李飞飞、杨乐坤、NVIDIA 等都在往这个方向做。

但佘昶也提醒，这件事还远没有共识：

> “什么是 world model，这个定义都没有一个共识。”

这段的价值在于，它没有把 world model 当成热词复述。它把视频生成的穿帮，连接到模型是否理解物理世界的问题。这里既有 engineering：大量视频数据、simulation data 怎么管理和使用；也有 research：world model 到底怎么定义，架构最后会怎么收敛。

## **52:00｜LanceDB 的市场：research lab 和企业多模态数据**

最后我问佘昶，LanceDB 的 vision 和 TAM 怎么看。

他先从 research lab 讲。AI company 和 research lab 的 training budget 每年加起来超过一百多个 billion。如果一个 lab 花 training budget 的 1%，能把 research velocity 提升两三倍，他认为这是很容易做的 tradeoff。

lab 之外，是企业多模态数据。AI 之前，大家通常叫它非结构化数据。企业里有海量 PDF、slides、sales calls、SharePoint 文件。这些数据越来越需要被管理、提取 intelligence，并在上面建立 knowledge layer。

所以 LanceDB 看的是两个市场：前沿 AI lab 的 training data 和 research workflow；企业里的多模态、非结构化数据管理。

这个判断也解释了为什么 LanceDB 不应该只被理解成 vector database。向量检索只是入口，更大的问题是企业和 lab 如何管理越来越多 AI-native 的数据。

## **54:00｜为什么 YouTube 式的视频检索还没真正做好**

我举了一个自己的需求：我希望可以一句话检索到视频里的所有相关片段，把视频变成各种 text 形式，甚至多语言处理。现在很多方案是先 transcribe，再用文字检索，最后映射回时间戳。但这还不是直接在视频内容里搜索。

佘昶说，这里有模型层面的瓶颈：怎么把视频向量化。

图片向量化已经有比较成熟的模型，甚至可以做 multi-vector，让图片搜索更准确。但视频是 time series。只抽帧再用图片搜索，会丢掉时间信息。直接生成 video embedding 的技术还不够成熟，短视频可能可以，长视频的信息压缩会太厉害。

他说，直接在视频里搜索，瓶颈主要在“怎么样去向量化”。

这段很适合普通观众理解多模态为什么还早。我们想要的产品很清楚：一句话找到电影、课程、会议、播客里的具体画面和片段。但模型还没把长视频压成既可搜索、又不丢关键信息的表示方式。

## **58:00｜AI 还很早，个人数据产品可以建在 Lance 之上**

最后我问他，LanceDB 未来会不会做 to C 产品，比如管理 iPhone 里的照片、视频和个人数据。

佘昶说他们大概率不会做这类消费产品，还是会专注 enterprise data infrastructure。但他很欢迎新的 founder 基于 Lance 和 LanceDB 去搭建 consumer app。

这也是一个清楚的边界：LanceDB 做底层 infra，让上层应用去处理个人照片、视频、personal context 这些具体场景。

这期聊到最后，最清楚的一点是：AI 还很早。我们现在看到的模型能力，已经足够让人兴奋，但很多工作流还没真正改掉。图片还不能稳定指哪打哪，视频还不能被自然搜索，world model 还没有共识，企业多模态数据还大量沉在 SharePoint、PDF、slides 和 sales calls 里。

佘昶这期把这些问题都拉回同一个地方：数据怎么存，怎么搜，怎么回填，怎么做实验，怎么让 research team 少花时间在 pipeline 和 database engineering 上。

模型继续往前走，越来越多进步会来自数据质量、数据混合和研究循环速度。LanceDB 想做的，就是把这套循环下面的数据系统先搭出来。
