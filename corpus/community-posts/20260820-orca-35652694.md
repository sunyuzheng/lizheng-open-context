AI 越能干，人可能越忙。

只开一个 Claude Code，你像是多了一个助手。等五个窗口同时跑起来，情况就变了：谁卡住了，谁已经做完，谁正在沿着一条错误路线越走越远，你开始记不清。每个任务都要查看、催促、解释和收尾，十个 AI 就会制造十份新的管理工作。

我和梁津晶的这期访谈，最先讨论的问题是：**当 AI 可以同时做很多事，人到底应该在哪里出手？**

聊下去，我们又追问了两件我一直很想弄明白的事。

Orca 只有四个人。为什么 Anthropic、OpenAI，以及同样很受开发者欢迎的 Pi、OpenCode，都没有先把这套东西做出来？

梁津晶几次创业，也没有追着当时最热的叙事跑。为什么硅谷不少一线创业者敢沿着自己的兴趣和 vision 往前走，最后反而做出一个现象级产品？

梁津晶是我在 Cornell 的学妹，毕业后先在 Google 做工程师，后来离职创业。她现在和三个伙伴一起做 Orca。录制这期时，Orca 在 GitHub 上已经接近 5 万颗星。

项目地址：[GitHub · stablyai/orca](https://github.com/stablyai/orca)

第一个问题，她给出的答案很具体。能稳定重复的过程，就让它自己跑；遇到重大歧义，AI 必须停下来；请人决定时，不要只丢来一句问题，先把方案做成一个能看、能批注、能快速判断的页面。

她分享过一位 Cloudflare 工程师的用法：每天有二十个 PR 要 review，他让一个总控 agent 拆成二十路，同时检查。梁津晶自己在 Orca 里积累了 400 多个独立代码工作区，其中 200 多个已经变成定时运行的固定流程。日常发布、bug 收集和社区信息整理，也有 agent 自动推进。只有遇到必须由她决定的地方，系统才发消息把她叫回来。

对我们多数人来说，400 不是一个值得模仿的数字。真正值得学的是另一件事：**你离开以后，工作还能不能继续；三天后回来，能不能找到现场；AI 需要你时，带回来的是一个清楚的选择，还是一团新的麻烦。**

## 02:29｜一个 AI 是助手，五个 AI 就成了管理问题

在 Orca 里，二十个 Linear ticket 可以直接变成二十路并行工作。进展会回写 Linear，后面的 code review、测试和结果展示也接在同一条流程上。

梁津晶把 Claude Code、Codex、OpenCode 这类负责执行任务的工具叫做 harness。它们会读文件、跑命令、搜索资料、改 code，一步步把任务做下去。Orca 没有再做一套自己的 harness。它处理的是上一层：很多任务怎样同时推进，谁遇到了阻塞，上下文怎样交给另一个模型，人应该何时回来，以及最后去哪里验收。

简单说，Claude Code 负责干活，Orca 负责让许多活不会彼此失联。

只做一件事时，一段聊天记录基本够用。任务多起来以后，你需要知道它对应哪个 ticket 和 branch，现在做到哪一步，关掉应用后能否恢复，最后应该交出 PR、测试报告还是一个页面，以及什么情况必须停下来问人。

搜索也因此变了。Orca 会同时索引 agent 的任务名、worktree 名和 Linear ticket。这里的 worktree，可以理解为每项任务自己的独立代码工作区。用户可能只记得“三天前做过一个登录问题”，不记得当时开的是哪个窗口。Orca 要帮他从这个模糊记忆回到原来的工作现场。

团队把这一整层叫做 ADE，也就是 Agent Development Environment。这个词是否会成为一个长期品类还不知道，但它指出的问题已经存在：AI 同时做的事一多，聊天窗口就不够用了。

## 13:41｜模型额度用完了，工作不能跟着停

Orca 可以把 Claude、Codex 和其他工具的状态放在同一个界面里。Claude Code 用到额度上限时，用户可以把上下文直接交给 Codex，让它接着往下做，不必重新解释一遍任务。

这对高强度用户很实际。今天适合 coding 的模型，下周未必还是同一个；某个 subscription 用完了，手上的工作却不能停。梁津晶录制时会在几个 provider 各买一两个约 200 美元的方案，再根据速度、能力和剩余额度分配任务。她估计，如果把自己的使用量全部按 API 价格计算，每月会到数万美元。

所以 Orca 所说的“中立”，首先解决的是工作连续性。模型和价格一直在变，任务本身最好不要跟着任何一家供应商一起被锁住。

## 21:03｜为什么四个人反而可能比模型公司更快

我追问她：这些功能，Claude Desktop 和 Codex 难道不会很快加上吗？如果 Orca 只是模型上方的一层界面，它会不会最终变成大公司产品里的一个 feature？

梁津晶先承认，Orca 和 Claude、Codex 的功能确实大量重合。今天领先几个 feature，不是一个永久的护城河。

她接下来的解释很有意思。Claude 和 Codex 团队内部的很多人处在 token 充足、资源宽松的环境里。他们未必会像外部用户一样，天天遇到额度用完、需要换 provider 接力，或者为了当天 ship 而在成本和速度之间做选择。Orca 的四个人每天都在经历这些问题，而且自己就是产品最激进的一批用户。

反馈经过的路径也短得多。梁津晶既是用户，也是产品经理和 builder。她碰到问题，今天就可以改；大团队往往要先做用户研究、整理需求、进入排期，再交给工程师。

还有一层是商业目标。Anthropic 希望更多工作留在 Claude 里，OpenAI 也希望用户继续用 Codex。Orca 恰好相反：Claude 进步，它可以接进来；Codex 进步，它也可以接进来。用户越需要在不同模型之间切换，Orca 越有价值。

Pi 和 OpenCode 又是另一种情况。它们允许用户接入很多不同模型，但用户仍然要采用 Pi 或 OpenCode 自己的 harness。如果你最喜欢的是 Claude Code 这套工作方式，换过去就必须做一次选择。Orca 尽量不让用户选边：Claude Code、Codex、Pi、OpenCode 都可以继续用，它只管理上面的并行、状态和交接。

这个选择也影响迭代速度。Claude Code 每次增加新能力，Orca 不需要先在自己的界面里重新实现一遍，用户可以直接用到第一方更新。兼容现有工具看起来没有“从头重做一切”那么有野心，却让四个人能够把精力放在真正缺失的那一层。

这给出了一个比“小公司更灵活”更准确的解释。产品速度与公司大小有关，也取决于谁每天亲自承受这个问题，以及解决它是否符合公司的利益。

当然，风险仍然存在。如果未来一家厂商同时赢下模型、coding agent 和团队协作，用户不再需要跨工具工作，独立 ADE 的空间会变小。梁津晶的判断是，多模型、多工具会长期存在。Orca 还需要继续证明这个判断。

## 29:28｜一个很小的功能，为什么做起来这么难

Orca 不是突然冒出来的。团队此前做了两年 AI testing agent，已经积累了管理 agent session 的经验。他们也是 Ghostty 和 iTerm 的重度用户，喜欢分屏同时跑几个 agent，也被一个很不起眼的问题反复折磨：应用一更新，原来正在跑的 session 就没了。

只开一两个 terminal 时，重新打开也就算了。一个人同时跑五十个 agent，就要重新分辨哪些还在工作、哪些已经结束、哪些 dev server 原本仍然开着。很多用户索性不更新。产品团队即使每天发新版本，用户仍然停在旧版。

Orca 因此要保存每个 terminal 背后的运行现场。应用更新后，聊天 history 要回来，原本正在运行的进程和 dev server 也要继续。保存和恢复本身不算神秘；几百个 terminal 同时存在时，内存、缓存、代码存储和状态追踪才是难点。

这个细节直接影响了 Orca 的迭代速度。用户相信更新不会弄丢工作，才敢每天更新；大多数人都在最新版本，团队收到的反馈才会更快、更一致。Orca 能够日更，一部分基础就来自这个看不见的恢复机制。

我当时在 34:36 说：

> “Prototype 到一个真正的 production，中间是有一个鸿沟的。你能力不够，是看不见这个鸿沟的。AI 可以更快把你带到鸿沟边上，但你想跨过去，还是需要很多时间、精力和水平。”

现在用 AI 做出一个能演示的版本已经很快。真正上线时，用户的一次更新、一个中断、几十个正在运行的进程，都会把 demo 里看不见的问题找出来。产品的 chasm 藏在这些地方。

## 35:54｜Orca 的 power user 到底怎样工作

我接着问她：你有 400 多个 worktree，到底怎么看得过来？

先要保证找得回来。任务一多，人不可能记住每个窗口。Orca 把 session、worktree 和 Linear 放在一起搜索，让用户从一个模糊的关键词回到几天前的工作。

接下来让 agent 管 agent。梁津晶看到的典型流程，是从一条 Linear ticket 开始，自动收集需求、写 design doc、做几轮 review、实现功能、打开浏览器或 mobile emulator 测试，最后交出 PR 和一份 HTML report。人先写清目标和验收标准，中间只在重大决定上介入，最后再看结果。

“介入”也需要提前设计。很多用户会要求 AI：如果有事需要我决定，先做一个 HTML 页面，把几个方案、界面效果和有疑问的地方展示出来。人看一眼，批注或选择，AI 再继续。对芯片设计、PPT、视频这类工作，最后还需要对应的 viewer 或 editor；一段纯文字很难让人完成验收。

流程跑通以后，再把它固定下来。梁津晶的 400 多个 worktree 里，有 200 多个已经是自动 SOP。Release agent 每小时检查一次发布进度，收集 Linear 和 Slack 里的内测 bug，自己处理能处理的部分，需要她时再发消息。Discord、微信和 X 上的信息也会先被自动整理。

所以她并没有每天盯着 400 个 agent。她花时间做的是：写清一个流程从哪里开始、做到什么算完成、哪些错误可以自己重试、什么情况必须来问人。工作三天后还能找到，换模型后还能继续，软件更新后还能恢复。

这些条件没处理好，多开 agent 只会多出一批失联的半成品。

## 45:55｜为什么她现在不再总选最强模型

一个月前，梁津晶仍然会把 coding 尽量交给当时最强的模型，便宜模型只运行已经验证过的 automation。后来她开始大量使用能力足够、但速度快很多的模型。

原因来自一次很实际的教训。最强模型也没有强到可以在关键 design 上跑两天而完全不看。她见过模型沿着一条错误路线工作两天两夜，等人回来时，已经在死胡同里走得很远。

只要人还要中途检查，项目花掉的时间就不只有模型运行的那部分。你还要等它返回，看它有没有走偏，再决定下一轮怎么改。一个能力略低、速度快三倍的模型，在需要反复讨论设计时，可能更早交出最终可用的方案。

她在 48:24 左右说：

> “既然人需要这么重要的参与，人的参与体验也是非常重要的。”

这给了我们一个很实用的模型选择标准：别只看 benchmark，算一算从任务开始，到你真正看过结果并确认可以继续，一共要多久。需要人频繁参与的任务，latency 本身就是能力的一部分。

## 55:28｜她为什么从婚礼直播一路转到 Orca

聊完 Orca，我们回到梁津晶自己的创业。

她离开 Google 时没有一个宏大的 AI thesis。第一个产品是给婚礼和公司活动做线上直播，赶上 COVID 尾声，很快有了用户和收入，也进了 Y Combinator。后来团队发现，这个生意的问题在频率：公司活动不够高频，婚礼更不会每个月办。每个月都要重新买一批用户，收入可以做出来，规模却很难继续长。

团队后来转向 Stably，用 AI 做软件测试，也拿到了企业客户。再往后，general coding agent 能做的事情越来越多。过去需要一款独立 devtool 完成的测试和内部工作，有一部分开始可以直接交给 coding agent。AI testing 原本清楚的产品边界正在改变。

于是他们把过去两年在 testing agent 里积累的 session management 抽出来，做成更通用的 Orca。

这几次转向没有一条事后编出来的完美路线。每一次都是某个原来的判断不再成立：婚礼直播卡在留存和频率；AI testing 则遇到 general agent 吸收垂直工具的趋势。团队换了产品，同时把已经学会的东西带到下一步。

这也是我从她身上学到的一个创业判断。一个产品走不下去时，值得先问两件事：当初哪条假设错了？前面已经建立的用户理解和技术能力，还有哪些能继续用？换方向不一定等于清零。

## 1:04:28｜Orca 几乎不做营销，为什么还能长得快

梁津晶说，团队大约 95% 的精力在做产品，5% 在想内容。Orca 所在的赛道本身就有很多人主动试新工具，GitHub 也会带来搜索和推荐。有人点进来并不难，难的是试过之后愿不愿意留下。

Orca 没有要求用户在自己、Claude 和 Codex 之间三选一。用户继续用原来喜欢的 coding agent，只把并行任务、状态、模型切换和验收放到 Orca 里。推荐给同事时，也不需要劝他放弃公司已经买好的工具，只需要告诉他：Orca 能让原来的工具更好用。

这也改变了他们做内容的方式。Claude 发布新能力，Orca 可以讲怎样在自己的工作流里使用；Codex 更新，也能做同样的内容。上游公司的每次发布，都给了 Orca 一个新的使用场景和传播入口。

团队还主动造了 ADE 这个词。GitHub 上开始有人搜索 “ADE” 或 “Agent Development” 时，Orca 是少数明确使用这个名字的产品之一。

兼容 Claude、Codex 是产品选择，也是它的分发方式。对四人团队来说，这种借力比不断制造营销话题省力得多。

## 1:09:21｜访谈 100 个用户，最重要的问题是“你已经花过多少钱？”

我问她：Google 和 Uber 都有很多优秀工程师，为什么有些团队能不断把产品做起来？

梁津晶说，他们每次开始一个方向，都会深入聊大约 100 个用户。不是发一百份问卷，而是逐个打电话，追问他们过去真的做过什么：

- 你为什么开始寻找这类产品？
- 在它之前，你试过 Zoom 或其他替代方案吗？哪里不够？
- 你已经为这个问题花过多少钱？

最后一个问题很重要。她不会问“你愿不愿意为我的产品付钱”。人很容易对一个设想表示支持，已经花掉的时间和钱更能说明问题在他心里的优先级。

她提到，当时的 YC group partner Michael Seibel 还要求 B2B 创始人了解客户去年的收入、增速和最大开销。你解决的问题有没有大到，让产品有可能成为客户很重要的一项成本？如果连客户的钱花在哪里都不知道，产品和宣传都容易隔靴搔痒。

问题确认以后，团队不会等着想出唯一正确的解法。梁津晶会尽快做出几版，再看真实使用。Orca 今天很关键的 agent status，第一版只是界面角落里一个几乎没人看的信息；团队换了好几次位置和呈现方式，才把它放到整个管理界面的中心。

她也坦率地说，这套反馈方法“不太科学”。PR、issue、社区讨论和数据都只是信息，最后仍然要由四个人决定做什么。团队之所以敢把自己当标准用户，是因为他们既有企业客户经验，又正好是一个每天高速使用 AI 的小团队。这个条件并不自动适用于所有创业者。

Product sense 在这里没有神秘答案。先追问用户已经做过什么、付过什么代价，再尽快做出一版放回真实使用里。数据帮你少猜一点，但不会替你做决定。

## 1:29:22｜为什么沿着兴趣和 vision 走，反而可能做出大产品

我最后把问题问得更大了一点：为什么硅谷很多优秀创业者，看起来不是先算出一个热门市场，再决定自己应该相信什么？他们往往从一个技术 insight、自己的兴趣，或者真正想解决的问题出发，最后反而做出很大的公司。

梁津晶的答案里，有一个很重要的环境因素。她在湾区看过太多公司从一个很小、很专注的问题里长出来。她举了同届 YC 的 Mintlify：它只专注把面向客户的 documentation 做好，但在她看来完全有机会成长为独角兽。Salesforce Ventures 已经投资了 Anthropic，仍然愿意投资 Mintlify。大平台的存在，并不等于应用层的机会已经被吃完。

这种经历会改变一个创业者对风险的感觉。梁津晶不把市场看成一张已经切完的饼。AI、机器人、生物、太空和传统行业里，还有大量东西没有被 build。一个点子不成立，世界上的机会并不会因此少一个。

她说：

> “机会总是有的。你当然要执行得非常好，但这个不行，我就再试下一个。无所谓，只要还有饭吃就可以。”

兴趣在这里也不只是“做自己喜欢的事”。梁津晶和团队每天都在高强度使用 coding agent，他们先成为这个问题最挑剔的用户，才看见大公司内部不容易看见的摩擦。长期待在一个真正关心的问题里，会积累技术直觉、用户理解和产品 taste。等市场开始需要它时，团队已经比追着新叙事进来的人多走了很远。

当然，兴趣本身不会自动变成成功。前面还有用户访谈、日更、production 工程和真实留存。Vision 决定一个人愿意把多少年放在什么问题上；市场最后仍然用使用和付费来验收。

婚礼直播没有走下去，但用户访谈和做增长的经验留下来了；AI testing 的产品边界变了，agent management 的技术积累被带进 Orca。Claude 和 Codex 发布新能力，也不一定是在削弱 Orca，有时反而会给它增加能力和流量。

硅谷的人力很贵，四人团队也不可能靠堆人和大公司竞争。梁津晶说，他们只能想办法让“一份力拆成十份用”。于是 release、社区整理和大量内部流程都被做成自动化。

我现在更愿意这样理解她的松弛：她没有把任何一个产品形态当成最后一把。每一步仍然做得很重，但下一次转向尽量不从零开始。

## 1:41:55｜最后，她还看好哪些 AI 创业机会

访谈结尾，梁津晶谈了三个近期判断。

第一个是 To C。AI 没有让 B2B 的采购周期明显变短；工具和模型变化太快，采购者有时反而更犹豫。与此同时，一个人做 app 的成本正在下降，用户也逐渐习惯为 AI usage 付费。她更看好让人做到过去做不到的事情，而不是再做一个与 TikTok 争夺时间的产品。

第二个是软硬件结合，尤其是中国创业者可以利用供应链和制造优势的方向。第三个是 compute，包括芯片、存储、模型 self-hosting、agent 运行环境，以及从芯片到生成 token 之间的软件优化。

我们后来又补了一类：传统行业。建筑、本地服务、采购和履约里，仍有大量十几年前留下的流程。最前沿的 agent 与这些行业每天真正怎么工作之间，还有一段没人替客户做完的落地工作。那里没有那么漂亮的 demo，却可能有最直接的时间、成本和收入回报。

## 结尾｜先别急着开 400 个 agent

回到这期最开始的问题：当 AI 可以同时做二十件事，人该在哪里出手？

梁津晶和 Orca 给出的答案，是先让工作本身变得可管理。重复步骤可以自动继续；方向不清时，AI 停下来；需要人决定时，先把问题整理成一个能快速验收的结果。模型可以换，应用可以更新，任务不能因此失联。

ADE 这个名字最后会不会留下，我不知道。只要我们仍在同时使用多个模型、处理许多并行任务，这个问题就不会消失。

对多数人来说，下一步也不需要开 400 个 worktree。先挑一件每周都会重复的工作，写清它什么时候可以自己继续，什么情况必须来问你，最后拿什么给你验收。把这一件事跑通，已经比多开十个聊天窗口有用得多。
